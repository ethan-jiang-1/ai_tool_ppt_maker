## 一句话

「水涨船高」——模型能力越强，prompt 应该越松（少束缚、多发挥），但不能松到丢了 PPT 的结构硬约束。Agent/workflow 调度层要精确；出图/出 HTML 的 prompt 层要对齐模型能力，剔除过度啰嗦的旧指令。

## Why

- 为弱模型（模型 A）调试好的详细 prompt，放到强模型（模型 B）上反而成了羁绊——过度指令限制了强模型更好的发挥
- 但 prompt 太松又有问题：KICKER/TITLE/SUBTITLE 位置、字体一致性这些 PPT 结构硬约束必须守住
- 非结构元素（视觉表现力、布局细节、色彩感受）可以也应该让强模型自由发挥
- 历史上 prompt engineering 的教训就是「越详细越安全」不总是对的——对强模型来说，详细可能是噪音

## 核心张力

```
Agent/workflow 调度层  →  精确、精准、别跑错  （该紧）
出图/渲染 prompt 层    →  对齐模型能力、别过度束缚  （该松）
PPT 结构硬约束         →  位置、字体、层级必须遵循  （该硬）
非结构表现力           →  容许模型最好地发挥  （该软）
```

## Current Direction（初步方向，待细化）

1. **prompt 分层**：结构约束（位置/字体/层级）与表现指令（风格/配色/布局感）分开
2. **模型能力感知**：不同模型（金星、后续更强的模型、HTML 渲染模型）各有自己的「最佳松紧度」
3. **剔除过期指令**：当模型升级后，review 并清理那些为旧模型写的过度约束
4. **度量难题**：怎么判断一个 prompt 是「刚好够」还是「过度束缚」？可能需要 A/B 对比或模型输出来回校准

## Design Questions

1. 结构约束和表现指令怎么在系统里分开表达？是两份 prompt 模板，还是同一份里用标记区分？
2. 「模型能力感知」怎么做——per-model prompt profile？自动检测模型代次？
3. 怎么判断一条指令是「必要的结构约束」还是「对强模型的过度束缚」？
4. 回退策略：如果松了之后强模型反而跑偏，怎么快速收紧特定页/特定元素？

## Non-Goals

- 不是要做一个自动 prompt 优化器
- 不是要放弃对弱模型的兼容
- 不是要每换一个模型就重写全部 prompt
