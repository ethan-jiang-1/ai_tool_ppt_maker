## Context

The change began with five mechanically invalid main specifications and a proposed rename of `legacy-image2-first`. Repository inspection showed that the old name was not isolated prose: markerless source detection, state healing, Controller ownership, CLI/status projections, transition identity, receipts, documentation, and fixtures all encoded a compatibility model. The current implementation still has concrete compatibility entry points: `state.mjs` upgrades old schemas, infers modes, and maps old controller nodes through `state-migration-map-v3.json`; `migrate-import.md` and the controller manifest name the transition; `05-iteration/migration/production_mode_transition.mjs` hosts it; HTML asset/config/renderer code accepts `_scratch/html-migration/projected-run`; and Phase-5 public exports plus doctor retain legacy bridge names. A partial implementation then replaced many tokens without completing the owning contracts, leaving syntactically broken tests, stale registries, contradictory main specs, and new phrases such as "explicit whole-page legacy compatibility" that preserved the obsolete concept under different words.

The intended product model is simpler. Both supported pipelines are explicit and current. A new or supported whole-page run always has durable mode state, uses normal `create-deck` ownership, and never enters a legacy-maintenance route. Cross-pipeline page-authority changes are clean-vNext state transactions, not source-to-HTML migration.

## Goals / Non-Goals

**Goals:**

- Restore structural validity for every checked-in main spec and preserve the still-valid behavior of repaired requirements.
- Make the current source, state, Controller, CLI, receipt, and documentation model internally consistent.
- Remove obsolete whole-page compatibility semantics rather than renaming their prose.
- Preserve deterministic repair for an already-supported current record while making every unsupported historical protocol non-writing and non-routable.
- Give future coding Agents one canonical vocabulary and a mechanically enforceable retired-token boundary.
- Keep verification proportional: exact static/token/inventory checks plus focused behavior tests, core, sweep, and affected E2E journeys.

**Non-Goals:**

- Do not provide aliases, persisted-data migration, markerless fallback, legacy receipt readers, or historical Controller continuation for removed whole-page protocols.
- Do not modify or use `deck_*`, `dpt_*`, or generated production artifacts as migration fixtures.
- Do not remove unrelated compatibility that still has an owning current requirement, such as generic diagnostic-envelope or schema readers; such uses require a narrow recorded exception and cannot label current whole-page work.
- Do not add a new governance capability for terminology; existing capability owners and framework verification own the change.

## Decisions

### 1. Use one canonical vocabulary at each layer

| Layer | Canonical current term |
|---|---|
| User production mode | `image2-only` |
| Whole-page pipeline | `whole-page-image2-v1` |
| Normal whole-page Controller | `create-deck` |
| Cross-pipeline Controller | `production-mode-transition` |
| Cross-pipeline public entry | `ppt_flow state --*-production-mode-transition` |
| Whole-page implementation | `04-image-production/whole-page` |

Active guidance may say "whole-page Image2" descriptively. It must not call the current route legacy, compatibility-only, maintenance-only, markerless, or a downgrade. The exact retired identities include `legacy-image2-first`, `legacy-image2-maintenance`, `legacy-image2-first-maintenance`, `LEGACY_PIPELINE`, `initLegacyBundle`, marker branch `legacy`, `migrate-html`, `confirm-html-migration`, `apply-html-migration`, `preview-html-migration`, `_scratch/html-migration`, and legacy-maintenance node/owner IDs.

The word `legacy` is not globally forbidden. Archived changes, explicit negative-test input, and unrelated compatibility contracts may retain it when their owning requirement explains the compatibility. Those exceptions must not route, classify, or describe current whole-page work.

### 2. Make source and state identity explicit and closed

The source parser accepts only direct scalar `production.pipeline: html-first-v1|whole-page-image2-v1`. Missing, malformed, indirect, retired, or unknown values fail closed with a bounded diagnostic naming both supported values. The only valid source/mode pairs are `whole-page-image2-v1` with `image2-only`, and `html-first-v1` with `html-only|html-then-image2`; every other pair is source/state drift and fails before Controller, journal, staging, or target mutation. Init writes the selected source marker and exact durable production-mode record. State/status/check paths do not infer a mode from missing metadata, generated bytes, Controller history, or directory shape and do not synthesize state for an unsupported old run.

The state reader classifies source, schema, run version, mode, and Controller identity before it invokes a repair writer. A usable current schema-5 record may receive only lossless canonicalization whose fields have a one-to-one meaning and which is blocked by a gate, reset, or transition fence. Observation always remains non-writing. A pre-current schema, a state whose run version is discoverable only from directory topology, or a state containing a retired Controller/node is a protocol mismatch: it is never upgraded, aliased, or resumed as current work, and observation leaves `state.yaml`, history, journals, and generated artifacts byte-identical.

This does not turn a user-visible syntax defect into a user task. When a current explicit run has a safely repairable current-v5 record, its owning execution path repairs and reports the canonical result. When the bytes cannot preserve current execution/evidence or establish the current identity, the state owner returns exactly one typed next action from its direct facts, never a Controller-assembled repair-or-recreate menu or raw YAML instructions. The Agent carries out that owned path and does not manufacture a continuation from legacy fields. The distinction is semantic: deterministic repair fixes a known current record, while compatibility migration would invent a new current route from historical state.

### 2a. Reuse the direct control path and keep transaction commits distinct from gate postures

This change adds no checker, cache, persistent control field, recovery command, or parallel success store. It tightens the existing source/state and transition owners so every affected surface reads the same direct facts and returns the owner's one nearest legal action. CLI-facing diagnostics reuse the existing `cli_error.mjs` `createCliNext` contract: an owner may select one existing action from direct facts, but this change adds no `recreate`, `replacement`, `migrate`, or generic recovery action type, command, or state field. `guide`, `confirm`, and `hard-stop` are policy outcomes only for human-centered gates; an exact production-mode transition plan commit is deliberately outside that taxonomy and does not introduce a new runtime schema or permission.

| Direct condition | Owning direct facts/evaluator | Control classification | One legal next action |
|---|---|---|---|
| Current schema-5 record has a one-to-one, fence-clear canonical defect | State owner over the selected source marker, durable state, exact run/version, mode, and active execution | `guide` | Owner repairs atomically, then reruns the same checkpoint; plain observation only reports that action. |
| Exact state-owned production-mode preview has selected target intake | Existing transition plan/receipt/CAS evaluator and its existing `transition_confirmation` record | Exact transaction commit, not a gate posture | Show the bounded target consequence and accept only the exact hash-bound commit. It records the target user's `proceed` decision, not a provider authorization, source-state waiver, or risk continuation. |
| Source/state identity, evidence preservation, journal ownership, or CAS attribution cannot be established | Existing state/transition owner over the direct bytes and bindings | `hard-stop` | Preserve the protected bytes, name the invariant, and return exactly one owner-selected typed next action through the existing diagnostic/inspection contract. Direct facts select the action; no force, inferred fallback, conversational continuation, or action menu exists. |
| A live writer or a changed journal/plan/receipt is observed | Existing journal/transition evaluator | `hard-stop` | Leave the writer and durable records untouched; rerun the owner's exact inspection/recovery checkpoint when its existing preconditions permit. |

The row labels deliberately do not create a generic recovery API. A `hard-stop` can lead only to the action the existing owner names after inspecting its direct facts; it never grants a human or Controller permission to rewrite state, receipt, or source bytes.

The existing transition commit records `transition_confirmation: { kind: "user", decision: "proceed", at }` for the explicitly authored target intake. It is a semantic target decision, not a `waived` gate decision: it carries no human-risk reason or continuation, accepts neither `--force` nor `--reason`, and cannot waive identity, CAS, journal, receipt, or provider-authorization checks. The state owner SHALL treat the target-intake object, its exact digest, and that decision record as one closed tuple before apply, recovery, or handoff; target `checkpoint-intake` preserves the confirmed decision time rather than inventing a later user decision.

The existing `transition_recovery_confirmation` is different again: it is a bounded human `no-active-apply` fact attestation inside a recovery `hard-stop`, not a risk-waiver `confirm`. Only the state owner may record it after the exact old-enough cross-host journal, source/target identity, plan, and token-derived journal bytes are current; every drift invalidates it and leaves recovery blocked. It carries no waiver reason, does not establish a target-intake decision, and never permits a live or still-uncertain writer to be overwritten.

For an unsupported historical source/state protocol, that existing CLI action is `repair_prerequisite`, already owned by `cli_error.mjs`. Its one default instruction preserves the old bytes and directs creation of a fresh explicitly initialized current run through `ppt_flow init`; it SHALL NOT say to repair, replace, migrate, or resume the historical state. Fresh initialization starts normal current authoring and carries no old state, receipt, approval, provider authority, generated artifact, or execution evidence. This is a terminal protocol result plus a fresh start, not a new recovery command, state field, or persisted-data conversion. A current-v5 record whose evidence cannot be preserved likewise receives one valid owner-selected existing action, but never a raw-YAML editing recipe or a fallback route.

### 3. Keep exactly one normal route and one transition route

`create-deck` owns new and continuing `image2-only` work, including style master, pilot, content/visual/header review, build, PPTX, notes, and final review. Deleted legacy-maintenance Controllers and their state-migration aliases have no replacement reader.

Cross-pipeline work uses the existing state-owned clean-vNext transaction. `ppt_flow` has exactly 14 top-level commands; there is no top-level `migrate-html` or `production-mode-transition` command. The transition Controller/file/state identity is renamed from `migrate-import` to `production-mode-transition`, because this change promises no persisted compatibility and the old name no longer describes its responsibility. Its implementation moves out of the Phase-5 `migration/` adapter and behind the state-owned public interface; Phase 5 may classify a request but cannot become a second transition authority. Candidate and journal ownership remains under `_scratch/production-mode-transition/` and the existing transition receipt family.

The transition is a version handoff, not a content converter. It may carry stable source/version/order bindings required to protect the source, but target source/control/intake must be explicitly authored as target-owned inputs and pass the target's normal content and visual checkpoints. Source prompts, pixels, generated artifacts, approvals, provider authorization, and Controller decisions cannot silently become target content or evidence. This keeps Agent process ownership and human semantic/quality judgment in their existing target-stage boundaries.

### 4. Decommission real compatibility surfaces by owner

Retiring the vocabulary requires removing the owning behavior, not merely its labels. The implementation work and verification use this concrete inventory:

| Surface | Current evidence | Required end state |
|---|---|---|

| Controller and transition ownership | `playbook/migrate-import.md`, `controller-manifest-v3.json`, state records, and `05-iteration/migration/production_mode_transition.mjs` | One literal `production-mode-transition` identity, state-owned transaction interface, no `migrate-import` alias or Phase-5 migration owner |
| Retired HTML candidate overlay | `html_asset_catalog.mjs`, `visual_config.mjs`, `html_slide_contract.mjs`, `html_slide_renderer.mjs`, and `bundle_layout.mjs` accept `_scratch/html-migration/projected-run` | No candidate overlay, migration palette projection, scratch renderer context, old plan/journal/receipt, or layout allowance; target authoring stays within the current transition's confined source/control owner |
| Whole-page adapter bridge | Phase-5 `legacy*` exports, env-check's legacy-root probe, relocation/audit baselines, and legacy-named tests | Current `04-image-production/whole-page` public adapter is the only generation/style-master/contact-sheet/header-lock owner; no legacy-named bridge is needed to run or diagnose it |

The inventory is an implementation and test checklist, not an additional source of runtime truth. Each row has one owning capability; no replacement registry, state projection, or generic compatibility adapter is created to compensate for a deleted row.

### 5. Remove compatibility requirements instead of adding competing rules

Every main requirement that authorizes markerless parsing, state-absent whole-page observation, legacy maintenance, old HTML-migration commands/nodes/scratch, or old receipt lineage receives a complete `MODIFIED` delta or an explicit `REMOVED` delta with reason and current replacement. Adding a new current requirement beside an old compatibility requirement is insufficient.

Main specs are synchronized only from coherent delta operations. Terminology-only edits in a main spec still require the owning capability delta when the old wording is normative or changes how an Agent selects a path. The final synchronized diff must contain no contradictory current and retired requirements.

Before that preview, the specs artifact must contain deltas for the still-missing proposal capabilities: `bootstrap-env-guidance`, `environment-check`, `framework-directory-layout`, `framework-script-layout`, `header-lock`, `html-slide-contract`, `html-slide-rendering`, `slide-identity-and-ordering`, `visual-asset-management`, and `visual-config`. Existing delta files must also modify every remaining requirement in their capability that still authorizes a retired scratch, Controller, receipt, or compatibility route. The first audit already identifies unsuperseded authorization in `commands-reference` refresh/iteration/title/structural guidance; `pipeline-orchestration` semantic refresh, Stage 2/pilot/header, structural materialization, and migration preview; `cli-surface` pilot/approve/status/build and historical transition state; and `playbook-execution` controller registration, routing, gates, exploration, resume, and recovery. Those complete requirement blocks must be copied and revised or removed before synchronization; an `ADDED` current-route requirement does not supersede them.

OpenSpec delta operations do not replace a main spec's `Purpose`. Before archive, the synchronized main specs for `bootstrap-env-guidance` and `environment-check` SHALL update their Purpose prose to name current Image2 readiness rather than a legacy/optional protocol; this is a direct main-spec synchronization edit reviewed with the merged delta result.

Coverage closes requirement by requirement, not when every proposal capability merely has a delta file. Before marking the reconciliation complete, maintainers SHALL construct a merged main-spec preview and classify every surviving reference to: an absent source/state marker, a current whole-page source described as historical/legacy/compatibility maintenance, `migrate-import`, old HTML-migration nodes or receipts, and `_scratch/html-migration/`. Each authorization-bearing main requirement SHALL have a complete `MODIFIED` replacement or an explicit `REMOVED` operation. A retained occurrence is valid only when it is a bounded prohibition/negative case or an independently owned exception with a named owner and reason, such as formal legacy slide IDs, a parser's historical diagnostic envelope, or the documented `doctor --image2` diagnostic alias. An adjacent current requirement, a prose-wide token scan, or a capability directory alone does not close that coverage.

The merged preview SHALL have no route from a missing source/state fact to a current Controller, no current whole-page route labeled legacy/compatibility/maintenance, no normal `migrate-import` Controller identity, and no HTML-migration scratch/receipt authority. The audit SHALL report the requirement heading for every allowed retained exception so a later terminology check cannot hide a semantic regression behind a broad allowlist.

### 6. Treat token checks as a backstop, not the semantic proof

The terminology check scans active framework guidance, main specs, code identifiers, Controller/state registries, fixtures, and tests. It rejects exact retired identities and malformed replacement phrases such as `whole-page whole-page`. A small allowlist may cover archived/history text, negative-test literals, or unrelated explicitly owned compatibility, with owner and reason.

Behavior tests independently prove that missing/retired markers fail, a pre-current/retired state read preserves raw state and history bytes, no compatibility state or Controller is inferred, current whole-page creation succeeds, state-owned transitions remain offline until their later production boundary, and deleted public commands/controllers are absent. The transition/candidate tests must prove that source prompts, pixels, approvals, provider authorization, and generated evidence do not appear in the target baseline. This prevents a token-only rename from passing.

### 7. Repair invalid requirements in place and keep OpenSpec validation explicit

Each structurally invalid main requirement keeps its complete still-valid behavior and scenarios while gaining the missing scenario. `workflow-inspection` receives its real Purpose. `openspec validate --all` and strict change validation remain explicit maintenance checks rather than package-test dependencies on a global executable.

## Risks / Trade-offs

- [A shortened MODIFIED block deletes valid behavior on sync] -> Copy every still-valid scenario and inspect the merged main-spec diff before archive.
- [A broad word ban damages unrelated compatibility contracts] -> Ban exact retired identities and current whole-page misuse; require narrow owned exceptions for other uses.
- [Mechanical prose replacement breaks code or creates nonsense] -> Use identifier-aware edits plus JS parse/import checks and phrase-level negative scans.
- [Removing old Controllers leaves registries pointing at nonexistent nodes] -> Update Controller manifests, state migration maps, workflow ledgers, executable/return audits, source-test ownership, and relocation baselines as one inventory task.
- [Removing all healing would violate the framework's deterministic-repair contract] -> Keep current-v5, fence-aware, one-to-one canonicalization and one owner-issued typed recovery action; prove historical protocol reads make no writes or current-route inference.
- [Fixture failures obscure runtime defects] -> Convert canonical fixtures to explicit markers first, then evaluate remaining source/state/transition failures.

## Migration Plan

1. Complete capability deltas, including `MODIFIED`/`REMOVED` operations for every conflicting main requirement, and preview the synchronized main-spec result.
2. Gate state repair by current identity/schema, delete semantic state migration and legacy fallback projection, retain safe current repair, then prove rejected historical reads are byte-preserving.
3. Rename/re-home transition ownership, delete old HTML candidate overlays and whole-page bridges, then reconcile registries, receipts, commands, and current adapter imports.
4. Reconcile Agent-facing guidance and tests against the canonical vocabulary and exact 14-command surface.
5. Run parse/import checks, retired-token and inventory checks, focused source/state/CLI/Controller/receipt tests, core, sweep, affected E2E, and complete OpenSpec validation.

There is no persisted-data migration or rollback. Existing markerless/legacy run bundles are intentionally unsupported after this change and must be recreated through a current explicit init path.
