## Context

Change 1 supplies an exact local Node/Playwright/Chromium/font runtime. Change 2 supplies an opt-in `html-first-v1` source, a complete renderer-neutral `pptmaker-html-slide-plan-v1`, ten closed layout families, immutable geometry, strict visual config, a passive local asset catalog, source/font/capacity preflight, fallback/selection resolution, and stable fingerprints. The current orchestration intentionally stops after Stage 1 and rejects every HTML-first delivery route with `html_first_delivery_unavailable`.

The repository remains MD-controller-first. Playbooks own user intent, review, gates, and route selection; JS owns deterministic source resolution, rendering, evidence, state healing, and diagnostics. The change must make the new path usable without allowing JS to become a second workflow controller, and must atomically migrate the active workflow vocabulary so new and resumed sessions do not see two contradictory lifecycles.

The single completion line is a fresh init that, with no Image2 credentials or style master, can author valid structured slides, show real local HTML previews, obtain content/visual approval, and publish a current contact sheet, PPTX, and notes. Markerless decks remain operable through an explicit legacy controller. Change 4's paid visual-slot workflow remains unavailable and unregistered.

## Goals / Non-Goals

**Goals:**

- Render every valid Change-2 family deterministically with exact geometry, local fonts/assets, actual browser measurement, and zero network.
- Publish self-contained per-slide HTML and verified PNG final slides through atomic, receipt-bound manifests.
- Make Stage 4 consume provider-neutral final-slide evidence and preserve Stage-5 stable-ID notes.
- Make HTML-first the new-deck/template default and expose complete preview/build/local refresh/structural materialization.
- Define review freshness that shows real compositor output without staling the whole deck for ordinary copy edits.
- Atomically migrate workflow directories, Phase/module enums, playbook controllers, state, guidance, links, and resume behavior.
- Preserve markerless legacy production and provide explicit, human-confirmed clean-vNext migration.

**Non-Goals:**

- Image2 visual-slot recommendation, planning, authorization, generation, candidates, promotion, cleanup, or modern `ppt_flow image2` commands.
- Whole-page Image2 changes, automatic prompt migration, provider calls from HTML rendering, or carrying legacy authorization into a migrated version.
- Arbitrary slide HTML/CSS/JavaScript, browser network access, system fonts, system browsers, or OS-independent pixel identity.
- PowerPoint-native editable text/chart objects, multiple visual slots, or changing the ten Change-2 family/source schemas.

## Decisions

### 1. One branch adapter selects a complete production implementation

`probeProductionMarker()` remains the earliest executable authority. `unified_pipeline` and `ppt_flow` select one complete branch adapter after canonical source selection:

```text
html-first-v1                     markerless legacy
Stage 1 structured plan           Stage 1 prompts/legacy plan
Stage 2 self-contained HTML       Stage 2 Image2 whole-page images
Stage 3 measured final-slide      Stage 3 header lock/passthrough
Stage 4 verified final-slide PPTX Stage 4 verified legacy final-slide PPTX
Stage 5 notes                     Stage 5 notes
```

The adapters expose the same orchestration-level operations (`validate`, `preview`, `build`, scoped rebuild, structural materialize) but keep their prerequisites and artifact paths private. HTML operations never initialize dotenv, credentials, style reference, or provider adapters. Legacy operations retain their current guards and manifests. Stage-number compatibility is retained for the unified CLI, but family/render logic lives behind the HTML adapter rather than in orchestration switches.

**Alternative:** replace legacy Stages 2/3 globally. Rejected because markerless decks still need their current renderer, review, and refresh semantics.

### 2. One opaque validated-run interface is the deep renderer seam

The new `html-slide-rendering` module exposes two orchestration-level operations over one framework-issued validated-run context and a closed request:

```text
buildHtmlPages(validatedRun, { slideIds, compositionVariant, dryRun })
  -> { plannedOrPublishedPages, currentManifest, diagnostics }

composeHtmlSlides(validatedRun, { slideIds, compositionVariant, dryRun })
  -> { plannedOrPublishedFinalSlides, currentManifest, diagnostics }
```

`validatedRun` is an immutable opaque context, not a caller-built bag. It binds the validated marker/plan, effective controls/catalog/fonts, exact discovered runtime/package roots, logical version, exact `publicationScope: canonical-run|migration-preview`, and nullable `htmlProductionResetId` (current state value for canonical, null for migration preview). Canonical Stage-1/run validation issues the ordinary context; only the closed migration projected-run validator may issue the scratch context. Callers cannot separately pass theme, assets, fonts, receipts, paths, publication roots, reset IDs, fingerprints, selection policy, or browser configuration that could disagree with that context. Direct CLIs create only canonical contexts. The closed request accepts only canonical slide IDs, `dryRun`, and exact `compositionVariant: effective|forced-fallback`; all family adapters, asset/font selection, receipts, fingerprints, scope/reset-specific manifests/publication, and internal browser seams stay inside the module. Family components consume only resolved boxes and versioned theme tokens. They do not parse Markdown/YAML, choose layout, or mutate source. Tests and CLIs cross this same interface. A closed component registry covers all ten families and typed blocks; adding a family/component/version requires a later contract change.

The migration scope maps internally and exclusively to `_scratch/html-migration/projected-run/`, whose complete candidate source/control/assets and scratch Stage-1 plan are receipt-validated as the anticipated target. Its manifests/receipts carry `migration-preview` and can satisfy only comparison-plan evidence, never canonical gates/state/build/PPTX/notes. Apply copies no scratch generated byte: it constructs a fresh canonical context for hidden vNext, rerenders, and compares ordered composition fingerprints, PNG SHAs, and contact-sheet SHA. Physical workspace paths and scope are excluded from HTML/PNG bytes and composition fingerprints so equality is meaningful; they remain included in manifests/receipts/locks so authority cannot cross scopes.

**Alternative:** one public renderer per family. Rejected because it leaks family schemas and invalidation rules into orchestration and tests.

### 3. Pages are self-contained; charts are produced as Node-side SVG

Each page is an inert UTF-8 HTML document with no external script, stylesheet, font, image, iframe, service worker, or network reference. The builder embeds:

- only the verified Source Sans 3 file and Noto Sans SC shards whose declared ranges cover the page's visible scalars, as WOFF2 data URLs;
- validated raster assets as data URLs and validated passive SVG assets inline;
- abstract-pattern/icon-composition output derived from versioned theme tokens;
- chart SVG generated before browser launch from exact direct dependency `echarts@6.1.0` in SSR SVG mode, with animation disabled and a closed option adapter derived only from the Change-2 chart record/theme.

The generated ECharts SVG is revalidated through a renderer-owned structural SVG-output check before embedding; source cannot supply ECharts options. URL-bearing attributes and CSS values are parsed against a closed data/fragment-only policy rather than rejected by substring. Inert XML namespace declarations such as `http://www.w3.org/2000/svg` are allowed. Every inline SVG instance derives prefix `pm-<first16hex>-` from SHA-256 of canonical `[slide_id, field_path, zero_based_occurrence, source_svg_sha256]`, then rewrites each `id`, `href`, and `url(#...)` reference; no random/process/time value is allowed. Typed icons still forbid `<text>`, while other permitted SVG text must use covered bundled fonts and pass the same browser font/measurement evidence as HTML text. The browser page contains no ECharts runtime or arbitrary JavaScript. Exact `echarts`, `zrender`, and lockfile versions plus license/audit evidence are checked during apply.

The renderer injects a fixed CSP equivalent to `default-src 'none'; script-src 'none'; connect-src 'none'; img-src data:; font-src data:; style-src 'unsafe-inline'; object-src 'none'; frame-src 'none'; base-uri 'none'; form-action 'none'`. It validates both markup and the browser request stream; CSP is defense in depth, not the only network guard.

**Alternative:** load ECharts JavaScript inside Chromium. Rejected because it widens the page execution surface and makes chart readiness/animation timing part of screenshot determinism.

### 4. The screenshot profile is versioned and browser measurement is fail-closed

The v1 compositor uses the Change-2 logical canvas `1000 x 562.5` CSS units and captures an exact `2000 x 1125` PNG at device scale factor 2. Before compositor implementation, one pinned-runtime probe must prove fractional clip semantics, repeated byte-identical nonblank PNG, timeout/finally cleanup, usable Range/SVG bbox evidence, CDP actual bundled-font glyph evidence for HTML/SVG and mixed English/Hans roles, and observable fail-closed denial for document/resource navigation, every forbidden scheme including WebSocket, and service-worker attempts. If any primitive is unavailable or nondeterministic, the artifacts are revised to a tested profile/evidence/re-encode path before implementation; the change cannot silently round, rely only on `document.fonts.ready`/CSP, or accept an unobserved route class.

Rendering launches only the paired Chromium with `--force-color-profile=srgb`, uses one browser/context per deck invocation and sequential pages, injects HTML through initial `about:blank`, blocks service workers, and treats every routed resource/navigation/socket request as forbidden regardless of scheme; `http`, `https`, `file`, `ftp`, `ws`, `wss`, `blob`, protocol-relative, and custom schemes have no allow path. Fonts/images exist only as embedded data bytes that do not create a routed external request. The renderer waits for `document.fonts.ready`, disables animations/transitions/caret, and closes pages/context/browser in `finally`. The context uses exact locale `en-US`, timezone `UTC`, `colorScheme: light`, `reducedMotion: reduce`, and `forcedColors: none`; the document uses `lang="und" dir="ltr"`. Renderer CSS fixes `line-break: strict`, `word-break: normal`, `overflow-wrap: normal`, `hyphens: none`, and `font-synthesis: none`. Authored Unicode scalar sequences are preserved as UTF-8 without normalization, and renderer/chart output performs no locale-sensitive number/date formatting. V1 evidence covers English plus Simplified Chinese/Hans in horizontal LTR layout only; it makes no RTL, vertical-text, full-CJK, or OS-independent pixel claim. Serialized self-contained HTML is capped at 64 MiB per page after construction and before publication/browser load. Composition uses exact `COMPOSE_PAGE_TIMEOUT_MS = 30000` and invocation timeout `COMPOSE_DECK_TIMEOUT_MS = 30000 + 30000 * selected_slide_count`; timeout reports the last normalized phase.

Every visible schema field has exactly one renderer-owned leaf marker and the observed marker set must equal the expected plan projection. Before capture JS checks root/slot scroll bounds, declared family box bounds, Range/text line boxes, every SVG text bbox, chart SVG bounds, image crop/focal-point bounds, visibility/opacity, and cross-owner overlap/occlusion using exact `GEOMETRY_EPSILON_CSS_PX = 0.5` (one output pixel at DSF 2). Escape/overflow greater than epsilon fails; non-overlay cross-owner intersection fails when both overlap dimensions exceed epsilon. Overlap is otherwise allowed only for exact registry-declared overlays; chart-internal marks remain within the chart owner's box. CDP font inspection proves non-zero custom-font glyph use for every rendered font role/family present. After capture, PNG decode proves dimensions and nonblank pixels. A failure publishes neither HTML-current nor final-slide-current evidence.

**Alternative:** trust Change-2 grapheme capacity. Rejected because source capacity is intentionally not browser pixel proof.

### 5. Immutable objects plus one manifest pointer define atomic publication

The canonical generated tree is:

```text
_generated/html_production/
  html_pages/objects/<html-sha256>.html
  html_pages/manifest.json
  final_slides/objects/<png-sha256>.png
  final_slides/manifest.json
  preview/objects/<contact-sheet-sha256>.jpg
  preview/plans/<review-plan-hash>.json
  preview/manifest.json
```

Raw HTML/PNG/contact-sheet object paths use the lowercase SHA-256 of their exact bytes, so “content-addressed” has one literal meaning. Composition/review/delivery fingerprints remain manifest semantics and never substitute for the byte address. HTML entries bind publication scope, slide ID, self-contained HTML SHA, composition fingerprint, renderer versions, runtime profile, and a slide-local composition input receipt. They do not bind whole source/plan bytes as currentness. Final-slide entries additionally bind exact `composition_variant`, measurement/font/network evidence, screenshot profile, HTML SHA, PNG SHA/dimensions, and the common provider-neutral final-slide fields. Raw HTML/PNG/contact-sheet bytes exclude publication scope, reset epoch, and physical workspace paths; their entries/receipts bind scope instead. Paths are owner-relative and confined by lexical/realpath checks. Current canonical delivery manifests use exact `pptmaker-html-pages-manifest-v1` and `pptmaker-html-final-slides-manifest-v1` and contain effective entries only; `pptmaker-html-preview-manifest-v1` may reference review-only forced-fallback HTML/final-slide objects and SHALL label their variant/digest explicitly. Canonical manifests/plans/receipts additionally bind the current nullable `html_production_reset_id`; migration-preview metadata uses null. Review plans use exact `pptmaker-html-review-plan-v1` immutable canonical JSON under `preview/plans/`; their hash excludes their own hash field and covers exact publication scope/reset ID/pipeline/logical run version/kind, approvable flag, fingerprints/outstanding evidence, input receipts, and referenced artifact paths/SHAs. Content plans include the complete ordered review projection; visual plans include system coverage/page dependencies and shown effective/forced preview refs. Reset ID remains outside composition/final-slide/delivery identity so safe byte reuse stays possible, but it is an independent freshness dimension.

Schema-v1 `preview/manifest.json` is the only current pointer and binds exact `publication_scope: canonical-run|migration-preview` plus independent nullable slots `review_plans.content`, `review_plans.visual`, `contact_sheets.visual_review`, and `contact_sheets.delivery`, each binding same-scope confined path/SHA and its owning digest/variants. Atomic preview-owner updates revalidate all carried slots, preserve unaffected current slots, and clear stale or cross-scope ones. Ordinary approval reads only a canonical matching plan slot; final review reads only a canonical delivery-sheet slot. A complete migration-preview slot remains comparison evidence, never target gate/delivery authority.

Each owner first rejects a state-owned reset in `deletion_pending`, resolves the current nullable reset ID, acquires transient exclusive `.publish.lock` through atomic directory creation, then exclusively writes canonical `.publish.lock/owner.json` containing schema, cryptographically random 64-hex token, exact owner kind/publication scope/reset ID/host/PID/epoch-ms, input-scope SHA, and prior-manifest SHA. Missing/invalid owner metadata is uncertain and not automatically reclaimable. A valid lock may be reclaimed automatically only when the exact host matches, PID is proven dead, and age is at least 60000 ms; every live/PID-reused/permission-uncertain/cross-host/invalid-clock case returns immediate `CONFLICT`. A scoped transaction revalidates every carried entry against current plan membership, publication scope/reset ID, and its own input receipt, drops deleted/stale/cross-scope entries even when they were outside the requested IDs, and orders retained/new current entries by current plan order. Reset status/ID is rechecked before manifest commit. Thus a scoped manifest may be incomplete but never falsely current; complete canonical delivery requires every plan ID.

New addressed objects are first written to exclusive same-directory `.object.<owner-token>.<byte-sha>.tmp`, closed and digest-verified, then atomically renamed to the raw-byte-SHA final path after rechecking absence; an existing final path must already match its address. This prevents a crash from occupying a final content address with partial bytes. After all objects verify, the owner rechecks the lock, receipts/realpaths and prior manifest SHA, then atomically replaces only `manifest.json` through `.manifest.<owner-token>.tmp`. Only the matching owner or valid stale-lock recovery may remove exact token-bound temps; recovery cleans them before starting a fresh transaction. The manifest is the single current-set pointer; no multi-file or directory rename is the commit point. Failed/interrupted runs leave the previous manifest and every object it references intact. Normal Change-3 publication never deletes final objects, so a reader holding the previous manifest remains valid; garbage collection is explicit future maintenance and out of scope.

Cross-host/uncertain publication locks have no targeted override. Recovery is whole-owner and scope-specific. For canonical publication, the gate journal must first be absent/resolved so generated audit bytes cannot disappear under an approval transaction; after explicit confirmation that no canonical writer/reader must be preserved, the Controller invokes only `ppt_flow refresh <run-dir> --kind reset-html-production --confirm-run-version <vN>`. The evidence module atomically writes version-scoped `html-production-reset` status `deletion_pending` with a fresh random 64-hex semantic reset ID plus a separate random owner claim/host/PID/claim time, makes matching HTML mirrors pending, and uses that record as a fence before deleting exactly the canonical generated owner. Only the current owner may delete/complete. A live same-host owner blocks; same-host dead ownership is CAS-claimable after 60000 ms, while valid cross-host/PID-uncertain ownership is claimable only through the human-confirmed route after 300000 ms; claim retains reset ID and replaces only execution ownership. On verified absence the owner marks the same record `complete`. A crash after invalidation remains safely over-invalidated: one claimant resumes the same reset ID and competing claimants yield. Complete+absent is idempotent only before authority is published in that epoch. If the owner disappears while gates/delivery/Stage-4/5 evidence is bound to the current reset ID, direct recreation is blocked and reset rotates a new ID even though deletion is already satisfied; owner absence without current-epoch authority remains an ordinary first/preview rebuild. Prior gate/delivery records remain immutable but stale by reset-ID mismatch, and rebuilt review-plan hashes bind the new ID, so identical raw bytes cannot revive prior authorization regardless of how the owner disappeared. For migration preview, after explicit confirmation that no migration writer/reader must be preserved, discard exactly the source run's whole `_scratch/html-migration/` transaction and rebuild candidate/comparison/plan evidence; canonical production/state/gates remain untouched. Neither path deletes one lock, cherry-picks objects, or crosses into source/control/legacy owners.

That manifest replacement rule applies to effective delivery and preview owners, not to review-only variants. `forced-fallback` rendering uses the HTML/final owner locks to write and verify immutable objects but never replaces those delivery manifests. The preview owner revalidates the returned receipts and makes the objects current only by committing a review-labeled plan/preview manifest. Failure between object preparation and preview commit leaves harmless non-current orphan objects. `dryRun` writes no object, manifest, lock residue, or generated directory.

**Alternative:** write page/final files in place and rebuild the manifest last. Rejected because a crash could expose mixed-snapshot files to Stage 4.

### 6. Per-slide composition identity excludes position; delivery identity includes order

`composition_fingerprint_v1` hashes renderer/compositor/component/chart/recipe versions, pinned runtime profile, exact `composition_variant: effective|forced-fallback`, the slide's complete renderer-consumed plan record excluding `position` and source locators, resolved theme, geometry, fallback/selection resolution, and referenced asset/font SHAs. `composition_input_receipt_v1` binds that same slide-local projection, current plan membership, and only renderer-consumed shared dependencies: effective visual config/geometry registry, referenced asset/font bytes, exact renderer/runtime/package versions, and their confined paths. It excludes whole source/plan SHA, order, notes, other slides, and unreferenced catalog assets; the whole ordered plan belongs only to delivery identity. Reorder, notes-only, or unrelated-slide edits therefore reuse unchanged HTML/final-slide bytes without allowing a removed ID to remain current. Normal delivery uses only `effective`. Forced-fallback pages have distinct identity, remain review-only, and cannot enter current delivery manifests or Stage 4. Copy, geometry, visual-system, fallback, runtime, or renderer changes invalidate only affected composition entries.

`html_delivery_digest_v1` hashes physical ordered slide IDs, their current composition fingerprints/final PNG SHAs, and the Stage-1 ordered plan digest. Stage 4 binds this digest in its receipt, so reorder rebuilds contact sheet/PPTX/notes order without rerendering unchanged slides.

### 7. Content and visual approval use authoritative version-scoped evidence

The human gate names remain `content` and `visual`, but HTML evidence cannot satisfy legacy gates or vice versa. State schema v3 expands the exact reserved-node set to `header-review`, `html-content-review`, `html-visual-review`, `html-delivery-review`, and `html-production-reset`. It reuses existing `nodes[id].by_version["3_versions/vN"]` storage; records/mirrors carry normalized `vN`, and no parallel top-level review/reset container is introduced. Absence of the target version's reset record means reset ID null. Both HTML gate records are scoped to the normalized run version/current nullable reset ID and are authoritative under `_state`. Deck-root mirrors are physically distinct: legacy retains `content_gate|visual_gate` and `_state.gates.content|visual`; HTML uses only `html_content_gate|html_visual_gate` plus run-version fields and `_state.gates.html_*`. No scalar mirror authorizes HTML Stage 4, and HTML approval never overwrites legacy authorization.

`content_review_fingerprint_v1` hashes the ordered human-reviewed content projection: stable IDs/order, headers, `visual_type`, concept, family body/callout fields, and structured fallback/brief semantics. It excludes notes, theme/runtime, source locators, and selection transport. A content edit or reorder stales content approval; notes-only and excluded visual/runtime changes do not. The record binds pipeline, run version, current nullable reset ID, fingerprint, status `approved|waived`, explicit waiver reason when waived, plan/preview evidence, and human decision/timestamp.

The deck-level `visual_system_fingerprint_v1` covers global resolved visual config, runtime profile, family registry SHA, and renderer/component/chart/recipe/compositor versions. `component_recipe_key_v1` is SHA-256 of recursively canonical JSON over family, geometry variant, ordered typed-block kinds, chart kind/series-category counts/formatter/legend resolution when present, and primary-visual kind plus abstract recipe or icon layout discriminator; it excludes ordinary text, numeric chart values, and asset bytes. Coverage keys sort by hash. For each key, the deterministic representative is the code-unit-smallest current stable slide ID, independent of position. Review shows its effective output and, when a current selection would hide the fallback recipe, its forced-fallback output too. Deleting the representative selects the next ID and requires new evidence for that key. The visual record binds current nullable reset ID, all current keys/representatives, preview manifest/path/SHA, review-plan hash, status `approved|waived`, explicit waiver reason, and human decision/timestamp.

`page_visual_dependency_fingerprint_v1` is deliberately disjoint from the global system fingerprint. It hashes page-local visual type, component recipe key, chart visual projection (ordered finite numeric values, excluding authored labels), primary placement/fit/focal point, effective fallback/selection state, and referenced fallback/selected/inline-icon asset IDs/SHAs; it excludes global visual config/runtime/renderer versions, ordinary visible copy, notes, and position. Each `page_reviews[slide_id]` binds that dependency fingerprint plus exact shown effective/forced-fallback composition fingerprints and preview SHAs for audit. A global system change requires new representatives for every current recipe key but does not independently stale unchanged page-local fingerprints. A new uncovered recipe key requires deck-level coverage review. A chart-shape change, page change within a covered key, or page-local asset/resolution change stales only affected page review; approving it refreshes the same record without reapproving unaffected coverage. If a selected asset is current, fallback review must visibly use `forced-fallback`. Broken selected bytes remain source-integrity failures, not reviewable changes. Ordinary copy changes stale neither global nor page visual evidence.

Preview publishes an immutable reset-bound hash plan and makes it current only through the preview manifest. Content plans always contain the complete current ordered review projection. Visual plans may reuse current unaffected evidence but are approvable only when the referenced shown artifacts cover every currently outstanding representative/page dependency; a scoped preview that omits stale evidence is explicitly non-approvable. HTML has no partial gate approval state. `ppt_flow approve <run-dir> content|visual --plan-hash <sha>` resolves that exact plan from the current preview manifest and records approval/waiver only when canonical plan bytes, SHA, reset ID, receipts, and referenced artifacts still match; waiver also requires a reason and binds the same complete plan. After approval, immutable plan/artifact bytes remain audit evidence and must still verify, but they need not remain the current preview pointer; gate freshness compares current reset ID plus content/system/page projections to the approved record. Thus copy-driven current preview replacement does not itself stale visual approval, while a full generated reset always does. Failure diagnostics never echo the content projection.

Deck-root mirrors are pipeline-disjoint. Legacy keeps metadata `content_gate|visual_gate` and `_state.gates.content|visual` unchanged. HTML writes only metadata `html_content_gate|html_visual_gate` plus exact `*_run_version`, and `_state.gates.html_content|html_visual` plus exact `*_run_version`; none is readiness authority. Gate records use `pptmaker-html-gate-review-v1`; delivery uses `pptmaker-html-delivery-review-v1`. Gate publication first canonicalizes state, then exclusively creates `_state/gate-approval-journal.json` with exact `pptmaker-html-gate-approval-journal-v1`, opaque owner token, host/PID/epoch-ms start/run version plus old/new state and metadata SHAs. While it exists, it fences all state and metadata-gate writers; only the matching owner may publish exact bound bytes. Plain observation does not heal-rewrite through the fence, and delivery-review publication conflicts. Same-host proven-dead ownership is automatically recoverable after 60000 ms. Cross-host/uncertain ownership requires Controller-obtained human confirmation and exact current token through `state --recover-gate-journal` after 300000 ms; a proven-live same-host PID remains non-overridable. The transaction atomically publishes authoritative `_state` evidence plus HTML-only state mirrors, updates only HTML metadata mirrors, then removes the journal. Recovery compares actual `(state, metadata)` SHA pair: `(old,old)` removes the uncommitted journal; `(new,old)` completes only the planned HTML metadata mirror; `(new,new)` removes the completed journal. One exact race projection also cleans without approval: state differs from old only by one same-version valid reset-pending record plus matching HTML state mirrors pending, while metadata is old or differs only by matching HTML metadata mirrors pending. That proves the gate new state never appeared and the uncommitted journal yields to reset. `(old,new)` and every other third SHA remain forbidden/ambiguous. All HTML state writers use expected-state CAS and recheck journal/reset state before rename, so a stale node transition cannot overwrite a newly published reset fence. Explicit recovery creates no decision. MD Controller owns showing artifacts/obtaining decisions and any cross-host stop confirmation; JS owns freshness and exact evidence.

All JS consumers cross one deep module seam in `scripts/lib/html_review_evidence.mjs`:

```text
inspectHtmlReviewReadiness(runDir)
recoverHtmlGatePublication(runDir, { confirmedOwnerToken } = {})
publishHtmlGateDecision(runDir, { gate, planHash, status, waiverReason })
publishHtmlDeliveryDecision(runDir, { decision, reason })
resetHtmlProduction(runDir, { confirmedRunVersion })
```

The module derives canonical paths/version, plan/artifact bytes, reset IDs, fingerprints, timestamps, and SHAs internally. Callers cannot pass mirrors, records, paths, reset IDs, digests, or timestamps as alternate truth. All five interfaces are synchronous, local-filesystem-only, provider/browser-free. Inspect is strictly read-only and returns normalized content/visual decision+freshness, outstanding recipe/page coverage, delivery freshness/decision, reset status, and exact bounded journal classification; raw evidence and reset ID remain internal. Gate recovery acts only on an existing journal with the exact matrix and cannot create a decision. Reset owns its state-first fence/mirror/deletion/completion transaction and accepts only exact run-version confirmation. Plain state/status and direct checkBundle inspect only; build, check-gates, and gate publication explicitly recover gate journals before inspecting/publishing, but no ordinary path auto-completes a reset.

The public Controller route for delivery publication is exact `ppt_flow state <run-dir> --record-delivery-review proceed|repair|redirect [--reason <text>]`. Repair/redirect require reason for durable resume; proceed forbids it. Gate-waiver and delivery reasons share one module-owned normalization: newline normalization, Unicode trim/no scalar normalization, no NUL/disallowed C0, non-empty, at most 1024 UTF-8 bytes, and no failure echo. The module validates the current node's declared decisions plus current reset ID and atomically writes both `html-delivery-review` and the current-execution node decision referencing it; no second `setNodeDecision` occurs. Repair reason re-enters pipeline-first ownership classification. Create-deck redirect resets to checkpoint intake; iteration redirect requires exact target `edit-text|edit-visual|edit-notes|restructure-slides|create-deck|stop`, and HTML cannot redirect into legacy maintenance. No destination is inferred from prose. The route accepts no evidence overrides and remains distinct from `approve` because delivery review is completion evidence, not a third gate. The existing state command also owns the explicit journal-recovery flag.

The only public route for the reset interface is `ppt_flow refresh <run-dir> --kind reset-html-production --confirm-run-version <vN>`. It is incompatible with explicitly supplied selectors, dry-run, and resolution/provider/base-url/model/style/force/reuse overrides; ordinary parser defaults do not count or flow into reset, and the confirmation flag is invalid for other kinds. The Controller supplies only the canonical version it has just shown to the human; the module creates/retains reset and owner IDs and resolves the exact generated owner internally. The result is bounded to `started|resumed|already-complete` plus rebuild/re-review required. This keeps a dangerous multi-file recovery behind one deep interface without adding another top-level command.

Publication locks, gate journals, reset ownership, and migration apply journals share one implementation-private owner-liveness classifier for normalized host equality, positive PID probing, PID-reuse/permission ambiguity, clock validity, elapsed age, and `live|dead-waiting|dead-recoverable|cross-host|uncertain|invalid` classification. Each protocol retains its own schema, age constants, confirmation/token rules, and recovery actions; callers never receive this internal seam. This concentrates OS/process edge cases without pretending the four transaction protocols are interchangeable.

Existing `checkBundle` remains synchronous and already owns canonical path SSOT. To avoid a static `bundle_layout`↔HTML-contract cycle, implementation uses one internal evaluator core: bundle layout builds a trusted context from its own constants/resolvers and calls the core; the public evidence facade builds the same context through bundle-layout exports and calls the same core. That core/context is an internal seam, not an orchestration interface and not caller-injectable. External tests cross the five public interfaces and `checkBundle`; filesystem/clock fault seams remain private. This preserves locality without changing every existing checkBundle caller to async.

### 8. HTML maintenance paths are ownership-based and remote-free

After marker classification, the change classifier maps HTML source changes to:

- Local Slide Rebuild: selected slide source/family/fallback change -> Stage 1, affected HTML/final slides, affected review, contact sheet/PPTX/notes.
- Local Deck Rebuild: visual config/runtime/renderer change -> Stage 1, representative preview/gate, all affected HTML/final slides, delivery.
- Notes-Only Refresh: notes and Stage 5 only when assembly lineage remains current.
- Structural Versioning Path: preview/hash-bound source transaction, hidden vNext validation/publication, then target-local HTML rebuild.

No HTML path imports the provider adapter or creates Image2 state/directories. Legacy requests retain Header Text & Style Refresh, Generated Image Rebuild, Notes-Only Refresh, and Structural Versioning Path.

### 9. Stage 4 consumes one provider-neutral final-slide contract

`render_artifacts.mjs` gains provider-neutral resolution through entries containing `slide_id`, `artifact_kind: final-slide`, `producer`, `final_slide_fingerprint`, confined relative path, SHA-256, pixel dimensions, and media profile. `final_slide_fingerprint_v1` hashes the common contract version, producer ID/version, producer-private current lineage fingerprint, byte SHA, dimensions, and media profile. HTML and legacy producers adapt their private manifests to this exact common shape. Stage 4 receives one explicit branch adapter, validates exactly one current entry per ordered plan ID, verifies paths/SHA/dimensions/profile/fingerprint, and never understands a render engine, private manifest schema, directory glob, or filename position. Only HTML `effective` variants are adaptable, and their private manifest reset ID must equal the current review snapshot. Its assembly receipt `schema_version: 2` binds the branch, plan SHA, nullable/required-as-applicable HTML reset ID and delivery digest, ordered IDs/images/fingerprints, and PPTX SHA. New Stage 5 requires that reset lineage and publishes notes receipt `schema_version: 3` over it; fully current markerless notes v2/assembly v1 remains readable under the compatibility rules, but no v1/v2 or pre-reset evidence can authorize HTML delivery.

### 10. New init is HTML-first; markerless legacy remains explicit

`initBundle` seeds the HTML-first marker, mnemonic identity scheme, structured authoring template, all five current preset-compatible visual tokens, and an empty v2 asset manifest/README. It does not create style master, legacy prompt outputs, Image2 refinement directories, or Image2 pending state. Intake asks content/visual questions but never asks the user to select a renderer.

Markerless sources remain `legacy-image2-first` at the adapter/controller boundary. No defaulting or state heal inserts the HTML marker into an existing source.

### 11. Legacy migration is a distinct hash-bound transaction

Migration uses a dedicated preview/apply operation, not ordinary source surgery. The Agent prepares a complete candidate source/control delta in a version-local `_scratch/html-migration/` transaction. Preview validates it as a projected HTML run, renders every proposed page locally, and produces a source diff, complete proposed contact sheet, exact plan hash, and exact `old_side_mode: verified-current|degraded-missing|degraded-stale`. `verified-current` requires one current common-adaptable legacy final-slide per current plan ID; migration builds the old comparison sheet locally from that set. A legacy Stage-2 raw contact sheet alone is not final evidence. Degraded modes show the final-slide evidence diagnosis/placeholder, never stale or missing bytes, make no parity claim, and offer separately authorized legacy maintenance if the user wants a verified old side; migration itself never calls a provider.

The canonical migration plan hash binds base/candidate source-control-asset receipts, anticipated visible target version, old-side mode/evidence, and ordered proposed composition fingerprints/final PNG SHAs/contact-sheet SHA while excluding scratch/hidden absolute paths. Preview renders only through the isolated reset-null `migration-preview` projected-run scope. Apply requires explicit human acknowledgement of that mode/hash, atomically fences itself with `_scratch/html-migration/apply-journal.json`, acquires the existing target reservation, rechecks base/candidate/old-side/target-name preconditions, copies only the authorized source/control/assets into a hidden vNext, and revalidates/rerenders that real target through a fresh reset-null `canonical-run` context regardless of source reset history. Target ordered composition fingerprints, final PNG SHAs, and contact-sheet SHA SHALL exactly equal the previewed proposal before an in-target success receipt and one same-parent no-replace visible-directory rename; any drift or output mismatch aborts and requires a new preview. It carries no generated legacy or scratch-preview bytes, reset/style-master requirement, provider/gate/delivery-review authorization, or prompt inference. The visible target's rerendered local artifacts are reviewable but cannot reach Stage 4 until target-version content/visual gates are recorded.

Normal apply requires the exact active source `migrate-import` apply execution for the confirmed plan/mode. The apply journal binds that execution ID plus random 64-hex token, host/PID/epoch, source/target, plan/mode, and exact reservation/staging basenames derived from target+token before the complete journal's first atomic write; it is not later patched to add paths. Every hidden-path/write/final-rename step rechecks unchanged journal bytes. The in-target success receipt binds the same execution ID and full source/control/output lineage. Same-host dead ownership is automatically recoverable after 60000 ms; cross-host/uncertain ownership needs human confirmation plus exact token after 300000 ms, while a proven-live PID cannot be overridden. If target is absent, recovery deletes only owned hidden paths/journal and fully rerenders from current preconditions; partial generated bytes are never resumed. If target exists, only its exact success receipt and output lineage permit idempotent cleanup/success. Any foreign path, journal drift, or conflicting target fails closed. This makes failure/crash recovery deterministic while leaving every visible version protected.

Because `_state` is deck-root while migration publishes a new run version, target publication and workflow handoff are deliberately recoverable rather than falsely multi-file-atomic. Exact target `_generated/qa/html_migration.json` (`pptmaker-html-migration-success-v1`) binds the source execution/plan/mode, source/control receipts, and target output lineage but carries no approval/completion meaning. After apply/recovery success, the Controller performs one ordinary atomic state write that completes the source migration execution and starts target HTML `migration-target-review` in Phase 3. If a crash lands between visible rename and that write, state/status recognizes only the exact receipt+active-source-execution pair as non-writing `migration_handoff_pending`; resume performs the handoff. Any mismatch fails closed. Target content/visual/delivery reviews remain pending.

Ordinary structural publication remains source-only and renderer-free. A later explicit HTML materialization may reuse prior immutable page/final-slide bytes only after recomputing matching target fingerprints and revalidating receipts. It copies verified bytes into target-owned object paths and publishes target-owned manifests bound to the target reset ID, initially null; no target manifest points across versions. Stable IDs/fingerprints authorize byte reuse only: version-scoped reset epochs, content/visual gates, metadata mirrors, delivery review, and final node decisions are never copied or relabeled. The materialization controller first publishes target reset-null Stage-1/2/3 plus exact review plans/artifacts and stops at typed `review_required`; target Stage 4 remains blocked for target-version human review even after reorder-only pixel reuse. After approvals, the same path revalidates and continues through delivery contact sheet/PPTX/notes/final review. Source publication and all materialization phases invoke no provider; unmatched target IDs may be composed only by the later explicit local materializer, never by source publication.

`state`, `status`, and `state --check-gates` probe the canonical marker before state interpretation. ## Risks / Trade-offs

- **[Change 3 is intentionally broad]** → Keep one vertical completion assertion and deep module seams; tasks are grouped by renderer, artifacts/delivery, workflow/state, migration, and verification rather than by file count.
- **[HTML embedding can create large page files and retained immutable objects]** → Embed only page-used font shards/assets, enforce the 64 MiB page cap, render sequentially, benchmark worst valid pages/decks, retain old objects for reader safety, and expose full `_generated/html_production/` deletion/rebuild only through the state-first reset transaction; object GC remains future work.
- **[A byte-identical rebuild could otherwise resurrect pre-reset approval]** → Bind review plans, content/visual gates, delivery review, and current generated metadata to a state-owned nullable reset ID; rotate it before full deletion or rebuilding an unexpectedly lost authorized owner, and make incomplete deletion a durable publication fence.
- **[Browser measurements can drift]** → Pin runtime/profile, version all rendering inputs, use exact screenshot goldens on the maintained Mac, and make cross-OS guidance non-normative.
- **[ECharts SVG may change across releases]** → Exact-pin `echarts@6.1.0`, disable animation, own a closed adapter/goldens, and include its version/output in fingerprints.
- **[State migration can misclassify old work]** → Inspect source marker before mapping, use a checked-in one-to-one map, preserve raw state on ambiguity, and require explicit human replacement.
- **[Default switch can strand newly initialized decks]** → Do not change init/template until renderer, assembly, gates, docs, and fresh E2E are passing together; commit the switch atomically.
- **[Legacy and modern manifests can cross]** → Branch-specific stage adapters produce one common final-slide evidence shape; tests trap cross-branch directories and provider calls.
- **[Visual gate can become too broad or too weak]** → Separate deck visual-system fingerprint from page review evidence and force fallback review even when a selected asset is current.
