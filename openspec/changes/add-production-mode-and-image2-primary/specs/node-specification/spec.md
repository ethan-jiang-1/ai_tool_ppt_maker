## ADDED Requirements

### Requirement: Production mode is authoritative per run version

Deck-root `_state/state.yaml` SHALL contain the only routing authority for production intent under
`production_mode.by_version["3_versions/<vN>"].mode`. The mode SHALL be exactly `html-only`,
`html-then-image2`, or `image2-only`, and every read SHALL resolve the caller's exact canonical
`run_dir` rather than a deck-global current value. The state owner SHALL be the only writer and SHALL
publish mode creation, migration, or mutation through its existing atomic expected-state/CAS boundary.
`history.jsonl` MAY record the event for audit but SHALL NOT participate in routing or recovery.

`project-metadata.yaml` MAY mirror only the most recently presented `production_mode` and normalized
`production_mode_run_version`. The mirror SHALL never supply a missing mode, override state, or satisfy
readiness. Status SHALL report missing or drifting mirror data and provide the state-owned repair path.
A valid mode whose derived pipeline differs from the exact run's canonical source marker SHALL produce
typed `transition_required|state_drift` evidence and SHALL block ordinary production before branch
readiness, generated-artifact inspection, or provider work.

#### Scenario: Exact version mode is inspected

- **WHEN** a command targets `3_versions/v2` while v1 and v2 have different mode records
- **THEN** the evaluator returns only v2's mode and derived policy
- **AND** no deck-global mirror or current-version guess changes the result

#### Scenario: Metadata mirror drifts

- **WHEN** authoritative v2 state says `image2-only` but metadata mirrors `html-only`
- **THEN** status reports repairable mirror drift while routing remains `image2-only`
- **AND** metadata cannot overwrite the state record

#### Scenario: Mode and source contract disagree

- **WHEN** state says `image2-only` for a run whose canonical source marker is `html-first-v1`
- **THEN** ordinary production hard-stops with typed transition/state-drift guidance before adapter work
- **AND** it protects attributable source/state identity without a force or waiver bypass

### Requirement: Missing production mode migrates once without runtime inference

State-schema migration SHALL populate a missing mode for each visible version only from its canonical
marker-probe result: the markerless `legacy` branch, normalized elsewhere as pipeline
`legacy-image2-first`, SHALL become `image2-only`, and the explicit `html-first-v1` marker SHALL become
`html-only`. Migration SHALL NOT add `production.pipeline: legacy-image2-first` to markerless source.
Refinement plans, attempts, candidates, accepted assets, generated bytes,
metadata, history, and controller position SHALL NOT imply `html-then-image2`. Migration SHALL preserve
all unrelated version keys and evidence and SHALL be idempotent once a valid record exists.

After this migration boundary, a missing, malformed, unknown, or noncanonical mode SHALL fail closed.
Observe paths SHALL not infer a replacement from the source marker or mutate the record merely to make
status pass; execution SHALL use the state owner's bounded schema repair/migration interface.

#### Scenario: Historical HTML state is migrated

- **WHEN** a pre-mode state has an `html-first-v1` v3 source and optional refinement history
- **THEN** schema migration records `html-only` for `3_versions/v3`
- **AND** it does not infer required refinement from that history

#### Scenario: Historical markerless state is migrated

- **WHEN** a visible markerless version first enters the state-schema migration path
- **THEN** the state owner records `image2-only` exactly once while preserving its existing behavior

#### Scenario: Written mode later disappears

- **WHEN** a previously migrated mode record is deleted or corrupted
- **THEN** routing fails closed and names the state-owned repair action
- **AND** it does not repeat source-marker inference or consult metadata/generated artifacts

### Requirement: Same-pipeline production-mode transitions preserve work

The state owner SHALL expose one atomic transition for `html-only <-> html-then-image2` on the exact
target version because both modes retain `html-first-v1` source ownership. The write SHALL use expected
state identity, append a bounded audit event, and re-evaluate completion from current authoritative
refinement evidence. Enabling `html-then-image2` SHALL make current refinement required and revalidate
any existing candidate/evidence; disabling it SHALL remove only the completion obligation and SHALL NOT
delete or rewrite refinement plans, attempts, candidates, accepted source assets, provenance, reviews,
or generated evidence.

Any transition between an HTML mode and `image2-only` SHALL return `transition_required` without state,
source, generated-tree, or current-version mutation. No `--force` or waiver SHALL turn that cross-pipeline
request into an in-place mode edit.

#### Scenario: Required refinement is enabled

- **WHEN** the exact current HTML version atomically changes from `html-only` to `html-then-image2`
- **THEN** status revalidates existing refinement evidence and reports any remaining completion work
- **AND** no provider request is made by the transition

#### Scenario: Required refinement is disabled

- **WHEN** the version changes from `html-then-image2` to `html-only`
- **THEN** refinement completion debt is removed while all attributable refinement work remains intact

#### Scenario: Cross-pipeline transition is requested

- **WHEN** a caller requests `html-only` to `image2-only` on the same version
- **THEN** state returns a versioned-transition requirement without mutating mode or pipeline-owned bytes

### Requirement: Published versions receive mode through an explicit state handoff

Every same-pipeline version publication SHALL invoke a state-owned idempotent registration after the
target is visible and before the publication operation reports complete. Registration SHALL accept an
exact source run and target run, read the source's authoritative mode, require the target marker-probe
pipeline to match that mode and the publication's expected target identity, and create only the target
`by_version` record through expected-state CAS. It SHALL never copy metadata, controller completion,
gates, refinement candidates, or generated evidence as mode authority.

If a process stops after target publication but before registration, ordinary target production SHALL
hard-stop with typed `mode_registration_required` and the same state-owned registration action. The
repair SHALL be mechanical and SHALL not ask the human to choose a mode. A conflicting target record,
changed source mode, pipeline mismatch, wrong source/target relationship, or state CAS drift SHALL fail
without changing either version. Existing explicit legacy-to-HTML migration MAY register `html-only`
only after its exact target success receipt is verified; no other cross-pipeline registration is allowed
in this change.

#### Scenario: Structural target inherits mode

- **WHEN** a source-only vNext publication produces a verified same-pipeline target from `html-then-image2`
- **THEN** the state owner records `html-then-image2` under the exact target version
- **AND** it does not copy source refinement or approval evidence

#### Scenario: Publication stops before mode registration

- **WHEN** a visible same-pipeline target exists but its bound registration did not commit
- **THEN** target production reports `mode_registration_required` and no adapter runs
- **AND** the Agent can rerun the exact idempotent registration checkpoint

#### Scenario: Registration relationship is ambiguous

- **WHEN** target pipeline, source mode, publication identity, or an existing target mode conflicts
- **THEN** registration hard-stops without rewriting state, source, target, or metadata

### Requirement: Production mode filters controller working sets without status forgery

Controller frontmatter MAY declare closed `supported_production_modes`, and a node MAY declare
`production_modes` as a non-empty subset of its controller's modes. The canonical playbook index SHALL
derive the active node-ID set from the exact run's authoritative mode before entry, successor, pending,
or completion evaluation. Nodes with no `production_modes` apply to every supported mode. Unknown modes,
empty/unknown subsets, a node mode outside controller ownership, or a controller mode incompatible with
`supported_pipelines` SHALL fail index validation.

An inapplicable node SHALL be absent from the active working set; it SHALL NOT be marked `skipped`,
completed, failed, or deleted from durable state. Existing records from another currently inactive mode
SHALL remain attributable but SHALL not satisfy or block the active mode. A same-pipeline mode transition
SHALL recompute the active set and revalidate retained records; if `current_node` becomes inapplicable,
the state owner SHALL move the pointer to the nearest declared mode-transition/handoff node without
inventing completion. `skipped` SHALL retain its existing meaning of an explicit human-authorized
bypass.

#### Scenario: Image2 branch is inactive under html-only

- **WHEN** `create-deck` runs in `html-only`
- **THEN** whole-page Image2 nodes are outside the active node set and have no synthetic skipped records

#### Scenario: Mode transition reactivates retained branch work

- **WHEN** `html-only` changes to `html-then-image2` after prior refinement work exists
- **THEN** refinement nodes become active and their retained records are revalidated for the exact version
- **AND** no record is accepted merely because it exists

#### Scenario: Inapplicable current node is transitioned safely

- **WHEN** the current node is no longer applicable after a same-pipeline mode change
- **THEN** state records the declared handoff pointer through CAS and preserves the prior node record
- **AND** it neither clears the execution nor labels the node skipped

### Requirement: Image2-primary final review binds current delivery evidence

For a durable first-class `image2-only` `create-deck` execution, the state owner SHALL record the
final-review node's typed `proceed|repair|redirect` decision only after resolving the exact normalized
run version and current whole-page content/visual decisions, version-scoped header review, ordered final
contact sheet, PPTX, and notes receipt. The node evidence SHALL bind confined paths and current SHA-256
values plus the active execution ID; callers SHALL NOT supply those lineage fields. Any bound artifact,
header evidence, version, or execution change SHALL stale the decision.

The MD Controller SHALL show the resolved artifacts and obtain the human decision, then invoke only
`ppt_flow state <run-dir> --record-image2-delivery-review <decision> [--reason <text>]`. Normal `proceed`
requires complete current evidence; this change adds no Image2 final-review force/waiver. `repair` and
`redirect` require a bounded reason and leave completion false. This operation SHALL reject HTML modes;
the existing HTML-only delivery-review operation remains unchanged. Historical
markerless maintenance without a first-class create execution retains its accepted compatibility
final-review semantics.

#### Scenario: Image2-primary final review proceeds

- **WHEN** the Controller shows current whole-page contact sheet, PPTX, and notes with current gate/header evidence
- **THEN** state atomically records the evidence-bound current final-review node decision
- **AND** status may use it for `image2-only` completion

#### Scenario: Image2 delivery changes after review

- **WHEN** the final image order, contact sheet, PPTX, notes receipt, or header evidence changes
- **THEN** the prior Image2-primary final-review decision becomes stale

#### Scenario: Image2 final review lacks attributable bytes

- **WHEN** the current contact sheet or PPTX cannot be resolved and shown
- **THEN** final review hard-stops with the owning rebuild action and offers no force path

### Requirement: Image2-primary provider authorization is current and scoped

Before a durable first-class whole-page operation may submit provider work, the state owner SHALL
persist the active controller node's typed human authorization bound to exact normalized run version,
operation `style-master|pilot|build|refresh`, sorted stable slide IDs or the style-master role, safe
generation-profile fingerprint, positive maximum submission count, active execution ID, and decision
time. This reuses the accepted whole-page maintenance authorization boundary rather than creating a
second provider-attempt store. Init, mode selection, doctor/live probe, content/visual/header approval,
a prior operation, and conversation text SHALL not create authorization.

Immediately before transport initialization, CLI SHALL rederive operation/scope/profile/count and
require an exact current typed decision from the active first-class execution. Mismatch, stale
execution/version, expanded scope, or a different operation hard-stops before submit and returns to the
Controller's same authorization checkpoint. Proven zero-submit provenance/reuse SHALL neither require
nor consume a provider decision. Historical compatibility retains its existing maintenance-controller
authorization semantics.

#### Scenario: Authorized pilot scope matches

- **WHEN** the user authorizes the shown Image2-primary pilot IDs/profile/count and CLI rederives the same scope
- **THEN** CLI may enter the existing provider adapter for no more than the authorized scope

#### Scenario: Authorization scope drifts

- **WHEN** selected IDs, profile, operation, count, version, or execution differs at submit time
- **THEN** provider work hard-stops without submitting and requests a fresh typed decision

#### Scenario: Proven reuse needs no authorization

- **WHEN** current provenance proves the requested whole-page operation will submit zero provider work
- **THEN** the local/reuse path proceeds without creating or requiring provider authorization

### Requirement: State file is YAML at run bundle root

Every new or actively executing run bundle SHALL contain deck-root `_state/` with durable
`state.yaml`, the single truth source for the execution pointer, authoritative production mode, and
pipeline-owned review evidence. Historical markerless decks MAY lack `_state/` during structure-only

mode records before execution. `state.yaml` SHALL retain active playbook/current node, per-node status,
gate decisions/evidence, stack, waits/notes, deck metadata, and exact version-scoped
`production_mode.by_version`. Append-only `history.jsonl` remains reference-only and SHALL not
participate in routing or recovery.

Reserved system evidence SHALL retain the existing exact six IDs and by-version storage; production
mode SHALL use its dedicated top-level state-owned map rather than masquerading as a reserved node.
Existing gate-journal exclusivity, reset fences, reserved-record ownership, refinement promotion CAS,
read-only observation, and recovery rules remain unchanged. Whole-workflow status MAY compose state
with artifacts but SHALL not persist another mode, phase, or completion authority.

`RESERVED_NODE_IDS` SHALL remain exactly `header-review`, `html-content-review`,
`html-visual-review`, `html-delivery-review`, `html-production-reset`, and `image2-refinement`. Each
reserved record SHALL live only at `nodes[reserved_id].by_version["3_versions/<vN>"]`; its internal
`run_version` and all state/metadata mirror companions SHALL use normalized `<vN>`. Reserved records
remain outside controller working sets. `image2-refinement` remains the sole authority for its plan,
attempts, candidate reviews, promotions, and safe human decisions; the new production-mode map and
first-class Image2 controller-node decisions SHALL not duplicate that record.

The only additional allowed transient file SHALL remain `_state/gate-approval-journal.json`, with exact
schema `pptmaker-html-gate-approval-journal-v1`, 64-lowercase-hex `owner_token`, normalized host,
positive PID, `created_at_epoch_ms`, normalized run version, and exact old/new state/metadata SHA-256
fields. While present it remains the exclusive state/metadata-gate write fence. Recovery SHALL retain
the exact existing SHA matrix: `(old_state,old_metadata)` removes an uncommitted journal;
`(new_state,old_metadata)` writes only the planned mirror after revalidation;
`(new_state,new_metadata)` removes the completed journal; the declared reset-only projection yields to
the reset; and `(old_state,new_metadata)` or any unbound third state fails closed. Production-mode
writes SHALL not bypass this fence or reuse the gate journal as a mode transaction.

Automatic gate-journal recovery SHALL still require exact same host, proven-dead PID, and age at least
`GATE_JOURNAL_AUTO_RECOVERY_MIN_AGE_MS = 60000`. Cross-host or otherwise uncertain recovery SHALL still
require human confirmation, exact token, and age at least
`GATE_JOURNAL_EXPLICIT_RECOVERY_MIN_AGE_MS = 300000`; a proven-active same-host owner remains
non-overridable. Token, age, journal-byte, path, or SHA drift SHALL preserve state and fail closed.
Refinement promotion continues to reject active gate/reset fences and use expected-state CAS; promotion
stales prior HTML delivery review. Production-mode migration/transition/registration/mirror repair use
the state owner's ordinary expected-state boundary and SHALL not create another transaction journal.

### Requirement: State schema is explicitly versioned and migrated

`state.yaml` SHALL use schema version 4 while preserving whole-workflow timing, execution identities,
controller working sets, stack semantics, typed records, atomic writes, and reserved system records.
Read/heal SHALL apply one ordered idempotent migration chain from supported v1/v2 through v3 into v4.
The existing v3 migration SHALL first normalize lifecycle/module names, aliases, pipeline-specific
controller binding, stack frames, gates, times, and reserved records; the v3-to-v4 step SHALL then add
only canonical `production_mode.by_version` records using this change's marker-probe rule. A valid v4
record SHALL never be reinferred from source or derived artifacts.

Known one-to-one mappings SHALL preserve completed/skipped evidence, in-progress/failed status, typed
decisions, human waits, execution identity, stack position, gates, reset/refinement evidence, and
capability freshness. Markerless gate values/evidence SHALL retain whole-page semantics. For HTML-marked
v1/v2 state, scalar content/visual values SHALL remain audit/mirror status only and SHALL not fabricate
authoritative HTML review records. State predating reset support SHALL interpret absence as nullable
reset ID null and SHALL not fabricate a reset record. A historical in-progress markerless controller
MAY remain bound to declared compatibility maintenance while its exact version mode becomes
`image2-only`; this SHALL not route a fresh first-class Image2 execution through maintenance.
HTML-marked old state SHALL become `html-only` regardless of refinement history. Missing/conflicting
source markers or one-to-many semantic mappings SHALL return the existing typed replacement action
without rewriting or clearing state. Starting a new top-level execution still requires explicit
replacement authorization when the current execution is incomplete and preserves reserved records.

The bounded legacy-to-HTML post-publication exception SHALL remain non-writing during observation: an
exact current migration success receipt bound to the active source execution may yield
`migration_handoff_pending`, never generic execution rebinding. Resume SHALL complete the source
migration execution, register the verified target as `html-only` through the state-owned registration
boundary, and start target `migration-target-review` with reset absent/null and target reviews pending.
It SHALL copy no reset, approval, waiver, delivery review, node completion, or production mode from an
unverified source. Receipt/state/source/target mismatch remains non-writing
`replacement_required|CONFLICT`; post-v4 same-pipeline versions use their explicit registration
checkpoint rather than schema migration.

### Requirement: State and status expose mode-aware complete delivery

State SHALL reserve version-scoped `html-delivery-review` as system evidence, not a third pipeline
gate. New writes SHALL use exact schema `pptmaker-html-delivery-review-v2`; readers SHALL accept valid
current v1 records as complete without rewriting them. The v2 record SHALL bind `pipeline:
html-first-v1`, normalized `run_version`, current nullable `html_production_reset_id`, HTML delivery
digest, every reviewable delivery artifact actually present, typed human `decision:
proceed|repair|redirect`, nullable normalized `reason`, `evidence_complete: boolean`, bounded
`waived_checks`, and UTC ISO-8601 `decided_at`. Reviewable delivery evidence SHALL include current
target-version PPTX and contact-sheet paths/SHAs. Complete evidence SHALL additionally bind the
assembly-v2 receipt path/SHA and PPTX SHA plus notes-v3 receipt path/SHA. The record SHALL never invent
paths or SHAs for absent artifacts.

The v2 record SHALL retain the complete 17-field v1 set with the same names and add only exact
`pptx_path`, `evidence_complete`, and `waived_checks` fields. Artifact path/SHA fields for missing
lineage SHALL be present as null rather than omitted, and only fields covered by a `waived_checks` entry
may be null. Current `pptx_path`, `pptx_sha256`, `contact_sheet_path`, and `contact_sheet_sha256` are
never nullable for forced `proceed`.

Forced delivery SHALL resolve `pptx_path` only through the HTML Stage-4 canonical assembly/layout owner
and SHALL resolve the contact sheet only from the current canonical preview-manifest delivery slot for
the same reset/version. It SHALL not scan for a convenient PPTX or accept caller-supplied artifact
paths. Both resolved paths SHALL be confined and their current bytes hashed before publication.

Normal `proceed` SHALL have no reason and require complete current evidence. Forced `proceed` SHALL
require a normalized non-empty reason, current target identity, and reviewable current PPTX/contact
sheet, and SHALL record every missing/stale lineage check with `evidence_complete: false`.
`repair|redirect` SHALL retain their complete-current-evidence requirement, required normalized
non-empty reasons, and routing semantics. Reason SHALL not enter delivery freshness/fingerprint and
SHALL not be echoed in failure diagnostics. JS SHALL validate exact reset-ID equality and every
recorded current byte/lineage before accepting a decision; MD Controller SHALL show the contact sheet
plus PPTX/notes result and obtain the decision. Any reset-ID, delivery, PPTX, contact-sheet, or recorded
receipt change SHALL stale the record.

The same atomic state publication SHALL write the current final-review node's typed decision with
current execution ID and exact reference to this system record; checkpoint/verification branching
SHALL accept only that referenced decision and SHALL not rely on an unbound prior conversation or
duplicate later state write. On resume, `repair` routes its reason through mode/pipeline-first change
classification to the owning source/system/production repair node. For `create-deck`, `redirect` SHALL
retain explicit reset-to-`checkpoint-intake` semantics and clear downstream current-execution
completion before re-intake. For HTML iteration controllers, redirect SHALL enter shared classification
and require a separate typed target in exact set
`edit-text|edit-visual|edit-notes|restructure-slides|create-deck|stop`; whole-page Image2 routing is
invalid unless a versioned cross-pipeline transition has completed. `stop` SHALL leave the current
controller incomplete, set `waiting_for: user:resume-or-replace`, and make resume report a user pause
rather than an automatic next node. Free text SHALL not auto-switch playbooks.

For `html-only`, current HTML Stage 1-5 receipts, content/visual decisions, and
`html-delivery-review: proceed` SHALL report the accepted deck complete when no retained refinement
promotion has made delivery stale. Absent refinement or retained historical planned/rejected work SHALL
not create completion debt; unresolved chargeable attempts SHALL remain visible, and
an accepted promotion SHALL require the existing renewed final review before completion. For
`html-then-image2`, those same records SHALL report HTML delivery current but overall production
incomplete until the authoritative refinement lifecycle is current, required slots have an accepted
candidate or explicit current `use-html` decision as allowed by that lifecycle, promotion/local
recomposition is current, and a post-refinement final delivery review is current. For a first-class
`image2-only` create execution, completion SHALL use current whole-page content/visual/header, assembly,
notes, and the evidence-bound final-review node record and SHALL NOT require an HTML delivery or modern
refinement record. Historical markerless maintenance SHALL retain its accepted compatibility completion
projection. Status SHALL separately
expose mode, pipeline consistency, identity freshness, decision, evidence completeness, and the nearest
owning action; a human quality waiver never satisfies missing identity, provider authorization, or
attributable bytes.

#### Scenario: Notes change after final review

- **WHEN** the mode-owned notes stage publishes a new receipt/PPTX after final-review `proceed`
- **THEN** the prior delivery review becomes stale and status requests current final review

#### Scenario: Reset transaction is complete but deck is not rebuilt

- **WHEN** `html-production-reset.status` is `complete` while current reset-bound production/gates/delivery are missing
- **THEN** status reports reset deletion complete but deck completion false with local rebuild/re-review next action

#### Scenario: Final review chooses repair

- **WHEN** the human chooses `repair`
- **THEN** completion remains false and the controller routes to the owning repair node

#### Scenario: Final review chooses redirect

- **WHEN** the human chooses `redirect` with a reason
- **THEN** completion remains false and create-deck returns to intake or an iteration controller requests one exact typed target
- **AND** it does not infer a cross-pipeline destination from the reason alone
