## Context

The archived first production-mode change established a version-scoped mode SSOT and safely supports
only `html-only <-> html-then-image2` in place.  A cross-pipeline request deliberately stops before
mutating source, state, or generated work.  The framework already contains a bounded Image2-to-HTML
migration transaction, but it is fixed to an HTML-only target and is not the general user-facing mode
transition protocol; there is no reverse HTML-to-Image2 path.

The new operation must preserve both versions and their attributable work.  It also must not turn a
mode conversion into an HTML-quality initiative: the target HTML source needs to be valid and runnable
under the existing renderer contract, while aesthetic scoring, parity, premium-layout work, and new HTML
quality gates remain out of scope.  First-class Image2 quality and authorization boundaries remain
unchanged after an Image2 target is published.

## Goals / Non-Goals

**Goals:**

- Provide a complete, recoverable, clean-vNext route for every cross-pipeline pair:
  `image2-only -> html-only|html-then-image2` and
  `html-only|html-then-image2 -> image2-only`.
- Keep `_state/state.yaml` and its existing CAS/journal owners authoritative for intent, confirmation,
  target registration, execution handoff, and recovery.
- Preserve source version source/state/evidence/generated work unchanged and give the target only
  target-owned source, mode, receipts, and future completion work.
- Reuse the existing HTML migration path where its source/target/no-replace mechanics apply, and reuse
  normal Image2-primary production after an Image2 target becomes visible.
- Make the minimum transition proof explicit: exact source/candidate receipts, anticipated vNext,
  target mode/pipeline, and an exact human-confirmed plan hash.

**Non-Goals:**

- Improving, scoring, comparing, or otherwise judging HTML visual quality; adding an HTML style-master;
  or requiring visual parity between source and HTML target.
- In-place cross-pipeline mode mutation, automatic conversion from HTML prose/pixels to Image2 prompts,
  or copying generated bytes as target authority.
- Bypassing current Image2 provider authorization, quality review, provenance, header, PPTX, notes, or
  final-review rules.
- Replacing same-pipeline structural publication, HTML-only mode changes, or existing refinement
  semantics.

## Decisions

### 1. Use one state-owned versioned transition transaction

JS/state owns an exact source-to-target transaction and its expected-state CAS boundary; the MD
Controller owns intent presentation and the human confirmation.  The public workflow is:

```text
request target mode
  -> prepare explicit target candidate
  -> preview exact target/impact
  -> confirm exact plan hash and target mode
  -> apply clean vNext
  -> register target mode and declared controller handoff
```

The transaction binds the active source execution, source run/mode/pipeline, anticipated target version,
candidate receipts, target mode/pipeline, and plan hash.  It reuses the existing state/history writer and
mode-inspection evaluator rather than adding a deck-global transition scalar, a second journal, or a
second success store.  A stale state/candidate/plan or changed source pipeline hard-stops before any
reservation or target write; the nearest recovery is the same prepare/preview checkpoint.

Alternative considered: let `state --set-production-mode` create a new version implicitly.  Rejected
because a state operation would then own source authoring, publication, and recovery without an exact
visible candidate or Controller confirmation.

### 2. Treat target authoring as directional, explicit source work

For Image2-to-HTML, the existing structured candidate plus sparse overrides remains the HTML source
owner.  It is generalized to select `html-only` or `html-then-image2`; it may locally render the target
to prove the current contract can execute, but that output is deterministic operational evidence, not a
quality score or visual-parity gate.

For HTML-to-Image2, the Controller/Agent authors a canonical markerless whole-page candidate with the
normal source controls.  The system never derives prompts, render modes, visual assets, or Image2 quality
evidence from HTML source or pixels.  Preview is offline and source/control-bound; it reports later
`needs_render` and the existing Image2 authorization boundary rather than submitting a provider request.

Alternative considered: convert HTML structured fields automatically into Image2 prompts.  Rejected
because both page authorities have different authored contracts and the inferred result would be neither
reviewable source nor attributable user intent.

### 3. Publish source-first and register target intent only after proof

Apply revalidates the exact plan, uses the existing confined reservation/no-replace same-parent target
publication mechanism, and emits a target-specific success receipt.  The state owner then verifies the
visible target marker and receipt relationship before CAS-writing the target's `production_mode` record
and metadata display mirror.  It never invokes same-pipeline inheritance registration for a
cross-pipeline target.

The source version stays byte- and state-authoritative.  The target does not inherit source approval,
delivery review, provider authorization, refinement records, reset epoch, generated objects, or node
completion.  HTML targets retain target-local existing delivery/review work; Image2 targets enter normal
first-class pilot/build/review/authorization flow.  This preserves Image2 quality requirements while
keeping HTML quality criteria exactly where they already are.

Alternative considered: copy current source artifacts to make vNext appear complete.  Rejected because
it makes a pipeline conversion erase provenance and allows unreviewed target output to inherit delivery
authority.

### 4. Make handoff explicit, inactive work retained, and recovery idempotent

The Controller records a declared CAS-bound handoff only after target mode registration succeeds.  It
does not mark source nodes complete or skipped, delete retained work, or synthesize target completion.
The target starts the mode-compatible controller at its declared transition entry with pending
target-owned evidence; source execution remains inspectable history.  A decline leaves both source mode
and current pointer unchanged.

An owned transition journal fences concurrent prepare/apply/recovery operations.  Recovery uses the
actual visible target and bound receipt/bytes as truth: no visible target permits cleanup and a fresh
preview; a fully matching visible target permits idempotent registration/handoff; any conflict remains
a hard-stop for inspection.  This folds transition recovery into existing target-reservation and state
CAS patterns instead of adding parallel recovery rules.

### 5. Separate operational validity from quality evaluation

The shortest valid control loop is source candidate validation -> deterministic applicable preview ->
exact confirmation -> target publication.  The transition adds no HTML quality score, parity comparator,
retry heuristic, or extra reviewer.  Existing HTML source/receipt checks and human delivery decisions
remain in force, but this change does not make their decision semantic more demanding.  Existing
Image2-specific preview/review/provider/final-review checks remain the only quality controls for an
Image2 target.

This removes the competing notion that cross-pipeline conversion must prove a visual-quality equivalence
before it can be safe.  Diagnostics identify one earliest invalid authority/candidate/receipt and one
owning next action; they do not report inferred visual shortcomings as a transition blocker.

## Risks / Trade-offs

- **[Risk] A visible vNext exists before target mode registration.** → Preserve the target, report one
  idempotent state-owned registration/handoff recovery, and block ordinary target production until it
  succeeds.
- **[Risk] A conversion loses or reuses source evidence.** → Keep source untouched and create only
  target-owned records; test exact state/tree diffs around success, decline, and failure.
- **[Risk] HTML-to-Image2 accidentally makes a remote request during preview.** → Bind preview to
  offline candidate/source validation and prove zero provider transport until normal post-publication
  Image2 authorization.
- **[Risk] HTML visual quality becomes an unbounded transition debate.** → Require only the existing
  runnable source/receipt contract and current human-owned delivery process; add no new score, parity,
  style, or quality validator.
- **[Risk] Two controllers compete for one state pointer.** → Let state own the CAS-bound declared
  handoff and validate active mode/pipeline before either controller starts work.

## Migration Plan

1. Add state/CLI transaction inspection and exact source/target candidate contracts behind unit tests;
   preserve the current cross-pipeline refusal until the full transaction is available.
2. Generalize the current Image2-to-HTML migration to a target-mode parameter while retaining its
   no-replace and recovery contract; add the offline HTML-to-Image2 candidate path.
3. Wire controller guidance, handoff/resume, natural-language routing, and active guidance to the new
   transition owner.
4. Add integration and mocked-provider E2E coverage for both directions, decline/failure/recovery, and
   target-local evidence; verify no HTML-quality scoring or Image2 preview submit is introduced.
5. Run focused suites, full unit/E2E tests, CLI return audits, docs consistency checks, and strict
   OpenSpec validation before release.

Rollback before a visible target leaves the source untouched.  After visible publication, recovery is
forward-only through the exact target receipt/registration path; manually deleting target state, source,
or generated data is never a rollback mechanism.

## Open Questions

None.  The target-mode selection, explicit authoring, existing human confirmation, and existing
pipeline-specific quality boundaries are sufficient for this change.
