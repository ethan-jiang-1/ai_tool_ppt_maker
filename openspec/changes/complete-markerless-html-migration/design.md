## Context

The current migration transaction has sound preview/apply invariants but an
unusable entry condition for real markerless work.  Its candidate source is a
loose `_scratch/html-migration/slide-specifications.md`, while
`projected-run/` is erased and reused as a renderer publication workspace.
That shape requires an Agent to hand-create every HTML source/control artifact
before the first command, and a bare markerless `preview` fails before it can
give useful guidance.

The change remains a framework-maintenance change.  The MD Controller owns the
route and the Agent owns semantic conversion from legacy material into a
structured slide body.  JS owns deterministic scaffolding, validation,
receipts, rendering, topology, and diagnostics.  Human confirmation stays at
the existing exact preview hash/mode publication boundary.

## Goals / Non-Goals

**Goals:**

- Make the first migration command useful for a real markerless version.
- Keep all preparation writes isolated to
  `_scratch/html-migration/projected-run/` and make repeated preparation
  idempotent when its inputs match.
- Give the Agent a stable, bounded per-slide authoring handoff without asking
  it or the user to reproduce deterministic files manually.
- Preserve the existing preview/apply transaction: complete local render,
  exact candidate receipts/hash, hidden canonical rerender, no-replace
  publication, journal recovery, and zero provider work.
- Improve deterministic palette and markdown-heading diagnostics while
  retaining legacy parsing and topology guarantees.

**Non-Goals:**

- No automatic prompt-to-`SLIDE BODY` conversion, family inference, or
  automatic visual/content approval.
- No in-place markerless-to-HTML conversion, source state mutation, visible
  version creation during prepare/preview, or provider submission.
- No new top-level CLI command, generic hidden-file allowance, arbitrary HTML,
  or migration-specific state authority.
- No visual-language expansion; that remains Change 3.

## Decisions

### 1. A projected run is the sole prepared-candidate authority

`prepare` will create a target-shaped, version-local candidate under
`_scratch/html-migration/projected-run/`.  It owns the candidate source plus
the source/control/asset scaffolding needed for a future HTML run, a
preparation receipt, and an authoring checklist.  Generated preview output is
also rooted there, but is a separate derived owner that may be rebuilt without
touching candidate-authored source/control files.

The migration adapter will introduce a small candidate resolver with one
allowlisted candidate file set.  It produces the source/control/asset receipts
used by both preview and apply.  Preview clears or replaces only its derived
HTML publication owners, then uses the ordinary HTML validation and renderer
seams against the resolved candidate.  Apply copies only revalidated
candidate-owned source/control/asset inputs into a hidden target and rerenders
there; it never promotes scratch generated bytes, gate evidence, or approval
state.

Target metadata/state scaffolding is a candidate handoff template, not a new
state store.  The existing state/metadata owners initialize or publish actual
target facts during the existing migration handoff.  This keeps runtime truth
with the current owner and avoids a second migration readiness record.

For compatibility, an old loose scratch candidate is read only during an
explicit `prepare`; it can be copied into a newly prepared candidate only when
there is no conflicting projected candidate.  `preview` never performs that
copy.  If both locations disagree, preparation stops before overwriting either
one and reports the single recovery path.

**Alternatives considered:**

- Continue using a loose candidate beside a disposable projected workspace.
  This keeps the real authoring inputs outside the transaction whose receipts
  are rendered and applied, and repeats the current setup gap.
- Create a visible vNext during preparation.  This would make an incomplete
  draft appear published and weaken the existing no-replace boundary.
- Copy preview output to the target.  This would give scratch artifacts
  canonical authority and bypass target-local receipt checks.

### 2. Preparation is mechanical; structured authoring stays with the Agent

The preparer reads the markerless source only to establish stable ordering,
identities, reusable non-semantic metadata, and an authoring checklist.  It
seeds a valid HTML-first frontmatter/template shell and creates one checklist
entry per retained slide.  It does not turn `IMAGE PROMPT` wording into a
family, structured fields, fallback, or content claim.  The Agent reads the
legacy material, makes those semantic decisions, writes the candidate, and
then reruns the same candidate resolver/HTML validator.

The checklist is bounded and machine-readable enough for CLI output, but it
is a projection of the candidate validator rather than a competing pass/fail
authority.  Missing structured bodies and authored fields are `guide`
outcomes: the CLI identifies candidate path, slide IDs, required fields, and
the exact next command.  A malformed or ambiguous source identity, a
conflicting existing candidate, an unsafe path, or a live transaction owner is
a `hard-stop` because it protects source attribution, authored work, or
recoverability.  There is no migration `--force` or waiver.

**Alternatives considered:**

- Ask the user to hand-create every scaffold file.  That makes deterministic
  framework work a human burden and caused BUG-028/032.
- Generate slide bodies from prompt prose.  It would make invented semantics
  look like authored content and violates the Agent/human ownership boundary.
- Have `preview` call `prepare` as a convenience.  It creates hidden writes
  and can overwrite a draft while an inspection command is expected to be
  read-only.

### 3. Palette seeding has a fixed provenance and complete diagnostics

The named shipped preset supplies the closed HTML-first schema/form.  A fixed
legacy-token mapping retains compatible source visual tokens; unavailable or
invalid mapped tokens use the chosen preset's deterministic fallback and are
recorded as such in the preparation result.  This mapping is an explicit
implementation table, not an inference from prompt prose or color names.

The candidate palette is validated through the existing visual-config owner.
For an invalid candidate or preset/legacy combination, the owner emits a
bounded list of field-path differences with expected contract summary and
actual safe summary.  It does not print the whole authored palette, prompts,
or arbitrary JSON.  The same resolver is used by prepare, preview, and apply.

**Alternatives considered:**

- Require users to reproduce the exact HTML schema by hand.  This is the
  current BUG-022 failure mode.
- Make visual-config silently fill arbitrary missing HTML fields.  That would
  conceal source drift and produce a second defaulting authority.

### 4. Preview is an explicit guide before it is a renderer transaction

`migrate-html preview` first resolves the candidate state without writing.  A
bare markerless source returns a successful `preparation_required` guide with
the closed prepare syntax, permitted preset names, candidate location, and no
visible/source/provider side effects.  A prepared but incomplete candidate
returns `authoring_required` with the same bounded checklist.  Only a complete
candidate reaches the existing local comparison render and plan-hash output.

Source/candidate receipt drift after a preview, an apply journal conflict,
wrong exact hash/mode, invalid confinement, or target collision remains a
hard-stop.  The existing journal recovery path is retained unchanged.  These
outcomes implement the two durable policies in order: the gate policy sets
guide versus hard-stop and protects the non-bypassable invariant; the control
policy makes the candidate resolver and its nearest legal recovery action the
single direct path.

### 5. Slide parsing uses one exact grammar with a preamble phase

`parseSlideDocument` remains the shared parser.  It will recognize an exact
numeric `## Slide <number>:` heading using the existing stable-ID grammar.
Everything after leading frontmatter and before the first valid heading is
preamble, so section prose such as `## Slide Specifications` is retained
rather than treated as a malformed slide.  A heading that presents a numeric
slide candidate but fails exact grammar remains an error, including before the
first valid slide.  This prevents a typo from silently becoming preamble.

The change does not create a migration-only parser or relax the structured
HTML contract.  HTML-first and legacy callers continue to share the parser,
with legacy behavior otherwise preserved.

### 6. Topology has an explicit system-file exception

All topology walks will share one explicit system-entry predicate that permits
only basename `.DS_Store` where a directory scan permits system artifacts.
It replaces generic dotfile/`__pycache__` ignoring.  Known journals and locks
remain subject to their owning allowlist/recovery logic; an unknown hidden
entry is reported rather than skipped.  The migration scratch checker will
recognize the new projected candidate layout and still reject foreign paths.

## Risks / Trade-offs

- **[Risk] A selected preset may not perfectly preserve legacy visual intent**
  -> The preset is explicit, provenance is reported, and the human still
  reviews the full local proposal before applying.
- **[Risk] A pre-existing loose candidate might contain valuable work**
  -> It is never moved or replaced by preview; only explicit prepare can copy
  it into an empty candidate, and conflicts stop before mutation.
- **[Risk] A growing candidate tree could hide arbitrary scratch data**
  -> Candidate and derived owners use narrow allowlists; topology tests cover
  unknown hidden files, journals, and foreign children.
- **[Risk] Guide responses could be mistaken for a successful preview**
  -> They use distinct status/next-action output and do not emit a plan hash,
  comparison evidence, or version publication.
- **[Risk] Exact parser tightening could reject old prose**
  -> Preamble remains permissive; only numeric slide-like typos are newly
  rejected, with source line diagnostics and focused legacy regressions.

## Migration Plan

1. Add the candidate resolver, projected scaffold writer, palette seeder, and
   pure readiness/checklist projection with unit fixtures for synthetic
   markerless input.
2. Switch preview/apply to the resolver while keeping explicit, non-writing
   compatibility handling for a legacy loose candidate.  Prove candidate
   authored files survive preview and scratch generated files never reach the
   hidden target.
3. Update the CLI operation/return audit, parser, topology checks, playbook,
   and COMMANDS routing together so every documented action has an executable
   owner.
4. Add integration and E2E coverage for prepare, guide, authoring, preview,
   exact apply, drift/conflict/recovery, and no-provider boundaries; then run
   the repository suites.

No persistent source migration is required to roll out this change.  Prepared
scratch candidates remain unpublished and source-safe.  If a rollout must be
reverted, the old framework continues to leave source versions untouched; the
new framework's explicit compatibility guide preserves candidate work until a
supported preparer is available again.

## Open Questions

None blocking.  The selected preset names remain the existing shipped preset
registry; tests will make that registry and the fixed legacy-token mapping
explicit rather than adding a migration-local configuration format.
