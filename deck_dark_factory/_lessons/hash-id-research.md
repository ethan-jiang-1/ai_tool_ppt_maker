# Page Production Long Hashes: Research Note

> Scope: only `deck_dark_factory/1_upstream_raw_material/page-production-iterations/plans/`, read at `2026-08-05T20:46:26+0800`. This note uses repository-owned source, specifications, and the named deck records only. It makes no production-data change.

## Conclusion

The long strings are hashes, not the deck's human-facing page IDs. More precisely, they are lowercase 64-character SHA-256 digests of canonical JSON records (and, for raw images, of the exact bytes). They are content addresses, integrity checks, immutable-history links, and provider idempotency inputs. `canonicalJsonSha256` sorts object keys and hashes the resulting UTF-8 JSON with `sha256`/hex; a byte hash follows the same SHA-256/hex form. See `ppt_maker_harness/scripts/contracts/canonical_json.mjs:23-39` and `ppt_maker_harness/scripts/shared/identity/byte_hash.mjs:1-9`.

The real page IDs are already short: the four plans contain 13 distinct mnemonic `slide_id` values: `CommGo`, `ContGo`, `CostGo`, `DejaVu`, `DimGo`, `DkfGo`, `HireGo`, `OrchGo`, `PlatGo`, `RitGo`, `SysGo`, `TwoMet`, and `VpEng`. Their source records are the four `work-plan.json` files under this directory (each is canonical single-line JSON, e.g. `plans/185e5d973406581b7ed89dee0b8446f68c4c4f091cc1d9c684348515c7b9c80c/work-plan.json:1`). The formal product rule is deliberately human-oriented: two BlockCase semantic chunks, 5-8 ASCII letters, with 5-6 preferred; it is the stable identity across reordering and rendering changes. See `openspec/specs/slide-identity-and-ordering/spec.md:7-16` and `openspec/specs/slide-identity-and-ordering/spec.md:45-58`.

Therefore the right change is **not** “replace every hash with 4-8 characters.” Keep every full digest in canonical records, filesystem paths, validation, and provider calls. Improve the interaction layer by hiding internal digests by default and showing a collision-checked short display reference only where an operator needs to distinguish one plan/batch/attempt. The UI/controller must resolve that reference back to the retained full digest before it invokes the existing exact-hash protocol.

## Why a Global Shortening Breaks the Design

1. The schema rejects a non-64-character value before business logic runs. `assertDigest` accepts only `/^[0-9a-f]{64}$/` in `page_authority_progressive_schema.mjs:57-60`; the store applies the same rule before it constructs any canonical location in `page_authority_progressive_store.mjs:54-56` and `page_authority_progressive_store.mjs:280-303`.
2. The digest is not decorative metadata. A plan's exact digest is the path key and is checked before immutable publication/replay; the scope head binds that digest and the previous one. `page_authority_progressive_store.mjs:360-388` and `page_authority_progressive_schema.mjs:217-250`.
3. Batch authorization/generation requires the exact current plan and batch hashes, and reconciliation requires the exact historical plan plus attempt hash. This is the published CLI contract, not an incidental implementation detail. `openspec/specs/cli-surface/spec.md:381-419`; the current CLI validates and forwards those values unchanged at `ppt_maker_harness/scripts/ppt_flow.mjs:2311-2381` and documents the options at `ppt_maker_harness/scripts/ppt_flow.mjs:3150-3162`.
4. An attempt's full key becomes the provider idempotency key. Truncating it could make two distinct submissions look identical to a provider, or make a legitimate reconciliation unresolvable. The owner explicitly persists the request digest and idempotency key before the request. `ppt_maker_harness/scripts/shared/image2/page_authority_progressive_raw_owner.mjs:1271-1319`.

So the original idea is sound: full digests make irreversible generation and recovery exact. The UX problem is that the protocol leak is visible to people who need to discuss a page or approve a batch, not cryptographically address a record.

## Short-Reference Feasibility

The corpus has two real global collisions at a 4-hex-character prefix:

- `3e46`: `3e460c51b3450c54abd830e2306c212d1b11ee8fd721bd5665c23f74749238b7` versus `3e46b52be189c8d9ada525b00c43e7e16246c7b46b3e4e8569fcc5bce8330277`.
- `e2c5`: `e2c532a886da87bd716350fc5ad16a26b97b91f760c6299ec6be00d5d3761263` versus `e2c5cd3a12462db93e2d68eeacdc821215b152f7e7e40f375e735b08ef6fe283`.

The first pair is directly observable in `plans/671d455539b68490d527c37917a28ec9767f38b53c85a3b01d23ba79462ec76c/attempts/0727a229695d25129e4a23ada132acffd54e4fde2bcdf2eef8f5f0af9ca53170.json:1` and `plans/671d455539b68490d527c37917a28ec9767f38b53c85a3b01d23ba79462ec76c/attempts/3e46b52be189c8d9ada525b00c43e7e16246c7b46b3e4e8569fcc5bce8330277.json:1`. The second is visible in `plans/f520896be72de827557b7f4e890912d0233aa7133a0312d8736072b4e606ecce/pilot-evidence/1083b2deee02cb95009e0f241a3ae09af6c4c614270172e622760ec1b69f4c2e.json:1` and `plans/671d455539b68490d527c37917a28ec9767f38b53c85a3b01d23ba79462ec76c/attempts/e2c5cd3a12462db93e2d68eeacdc821215b152f7e7e40f375e735b08ef6fe283.json:1`.

There is no collision at 5, 6, 7, or 8 hex characters in this exact snapshot. That is an observation about this deck at the stated time, not a guarantee for later plans or a different deck. A fixed four-character global selector is already unsafe. A prefix that is initially unique may also become ambiguous when a future record is added, so a shortest-current-prefix must never become the persisted identity.

## Recommended UX Contract

1. For slide conversations, render `position + slide_id + title` and accept the existing `slide_id`/spoken selectors. That is exactly the system's intended user-facing selector model. `openspec/specs/slide-identity-and-ordering/spec.md:70-96`. Do not show a plan hash in that flow.
2. For plan/batch/attempt status, show a semantic label first, then an optional non-authoritative reference such as `plan 671d4555`, `batch 5e8784d1`, or `attempt 3e46b52b`. Use eight hex characters by default, scope the lookup by record kind and currently loaded deck/plan, and verify that it maps to exactly one retained 64-hex digest before it can drive an action.
3. Preserve the full 64-character values in artifacts, CLI transport, provider requests, output JSON, and all state comparisons. The controller/UI can hold the full value invisibly and send it to the existing command; no storage migration or history rewrite is needed.
4. If a future UX requires people to type a short reference into the direct CLI, add a separate, collision-checked resolver and an explicit option such as `--plan-ref`; do not reinterpret `--plan-hash` or accept an ambiguous prefix. This is a CLI/spec change because the current specification explicitly requires exact hashes and rejects friendly or inferred selectors for paid operations. `openspec/specs/cli-surface/spec.md:397-419`.
5. If a hard eight-character ceiling must hold forever, use a non-hash contextual handle such as `P01`, `B03`, or `A12`, derived from a retained view/registry and never included in canonical record bytes. A hash prefix can be collision-checked, but no truncated hash can promise uniqueness forever under a fixed length.

This preserves the safety model while removing the long opaque strings from normal human conversation. No production artifact in `plans/` should be renamed or manually edited as part of that UX improvement.
