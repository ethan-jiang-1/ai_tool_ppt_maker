# Agent — 一类以前根本做不了的新程序

> 核心判断：Agent 不是传统程序的增量改进。它是一个新物种——以前技术上就做不出来。而它的存在，动摇了传统 SDLC 最根本的前提。

---

## 以前根本做不了

Agent 是一类**以前不可能做的程序**。不是因为"以前没人想到"——是因为以前没有 LM 这种东西，技术上就做不出来。

- **传统程序**：确定性逻辑，同一输入 = 同一输出。行为可以被完整预期。
- **Agent**：程序里有 AI 在做判断、做选择、处理模糊性。它的行为不是完全确定的。

这不是"传统程序加了 AI 功能"——这是程序这个概念的**范畴扩展**。

---

## 它怎么挖了传统 SDLC 的地基

传统 SDLC 的全部方法论，不管瀑布还是敏捷，都建立在"程序是确定性的"这个前提上。Agent 把这个前提挖了：

| 传统 SDLC 的前提 | Agent 带来的挑战 |
|------|------|
| 程序的行为可以被完整预期 | Agent 的判断可能对可能错，行为有不确定性 |
| 测试 = 验证输入→输出的一致性 | 如果 Agent 的内部判断可以变化，"正确输出"怎么定义？ |
| Review = 检查代码逻辑是否正确 | 如果组件是 AI agent（它的判断可能对可能错），review 是什么意思？ |
| 版本 = 代码的快照 | 如果程序行为随着底层模型升级而变化，"版本"还意味着什么？ |
| 需求 = 可以被完整描述的功能 | 如果一个 Agent 的行为是 emergent 的，需求怎么描述？ |

---

## Agent 要求 SDLC 重新设计

不是"在现有 SDLC 上加一个 AI 阶段"。是**从地基开始重建**：

- **测试**需要从"验证确定性行为"变成"验证 Agent 的行为边界"——不是测它做了什么，是测它**不会做什么**
- **Review**需要从"检查代码"变成"评估 Agent 的判断质量"——人的审查对象从逻辑变成了判断
- **版本管理**需要从"代码快照"变成"代码 + 模型版本 + 行为签名的组合"
- **需求工程**需要从"完整描述"变成"设定边界条件 + 验收标准"

这些不是增量调整——是需要全新的方法论框架。
